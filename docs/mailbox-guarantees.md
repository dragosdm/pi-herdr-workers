# Mailbox guarantees

This matrix covers 106 executing cases across Phases 1 through 5, with 66 supported assertions and 40 known gaps. The Phase 3 watcher flake remains open. Run the tests with:

```sh
npm ci
node --import tsx --test tests/extensions/herdr-worker-pi-compat.test.ts tests/extensions/herdr-worker-mailbox.test.ts tests/extensions/herdr-worker-recovery.test.ts
```

The production transport publishes JSON through a synchronous temporary-file write and rename. The worker extension validates the claimed sender pane and invokes Pi's custom-message API. The transport retains the file while that filename is in flight. The `context` and `agent_settled` hooks acknowledge matching custom entries visible in SessionManager memory. Lifecycle entries also pass through the extension's existing handled/retry gate before cleanup.

A send receipt proves publication, not receiver acceptance or execution. A matching ordinary entry on a fresh receiver permits cleanup without reading the envelope again. In an existing receiver, a drain skips in-flight filenames before looking for matching entries, so the acknowledgement hooks still matter.

## Evidence limits

The controlled host separates its queue, memory entries, and a test JSONL file. The default `explicit` mode preserves separate consumption, append, write, reopen, and hook operations. Named `file-backed`, `deferred-first-write`, `disabled`, and `write-failed` modes model the storage boundaries for later fault tests. A deferred flush is explicit; a modeled write error occurs after memory insertion without rolling it back. These modes have fixture tests, but their JSONL is not Pi's session-file format. File-only reconstruction in the Phase 1 cases uses a fresh host in the same test process after stopping the previous receiver, not a process kill.

The Phase 1 acknowledgement cases deliberately write and reopen the test file before invoking the hook. That order proves those cases, not a requirement enforced by production. `getEntries()` does not prove a successful disk write. The real-Pi cases now execute the opposite order as known gaps. No case claims universal no-loss, exactly-once delivery, power-loss durability, or assignment completion.

Filesystem operations run under a private temporary root. Most watch and poll callbacks are captured and invoked explicitly. One bounded smoke test uses real `fs.watch` with polling disabled. Another makes watch creation throw, then invokes the poll callback. Fixtures dispose listeners and subscriptions, release blocked deliveries and assistant streams, dispose Pi sessions, reap owned children, and remove their roots. These tests need no Herdr panes, credentials, provider requests, or global Pi installation.

## Scheduling, rejection, and containment

The real-watch smoke test has an unresolved intermittent timeout on the September 6, 2026 macOS verification run. Watch creation returned, but no notification arrived within the unchanged three-second bound; the published file remained and the only snapshot was the empty startup scan. During Phase 3, five mailbox repetitions and the full suite passed, but an additional combined repetition failed. The Phase 5 recovery/mailbox repetition loop reproduced the same diagnostic on run 1 at 96/97 and exited before runs 2 through 5. Its focused command passed 132/132 and the later full suite passed 252/252, with verification commands run sequentially. The case remains enabled with diagnostics, and Phases 3 and 5 are not marked complete. This matrix does not establish reliable watcher-only delivery on that environment.

Each receiver drains one sorted filename snapshot at a time. A blocked delivery test proves overlapping watch and poll callbacks do not start another pass; a newly published file waits for the next drain. That is snapshot order, not producer order. Equal-timestamp suffixes can reverse calls, including bind-run and assignment publication. Forced filename collisions overwrite earlier payloads. Two receivers with separate in-flight sets can both inject the same file before either acknowledges it.

The listener marker is a PID liveness hint, not an exclusive ownership lock. A fixture-owned child exits before the dead-PID check; RPC send then chooses the modeled Herdr prompt fallback without publishing an envelope. No arbitrary PID or external pane is used.

Unreadable final JSON remains for a later drain; temporary `.tmp` files are ignored. Successfully parsed but invalid payloads are deleted. The real extension rejects unknown and stale peer panes. Lifecycle reports additionally require a matching saved run binding. An incoming unbound report is deleted, while an already recorded valid unbound report remains pending. The bound-report case counts one journal entry, one accepted lifecycle event, and envelope deletion separately from its custom-message injection.

A one-shot delivery rejection before `markInFlight` ends that pass and allows the next drain to retry. A modeled synchronous send throw after marking leaves that receiver stuck; stopping it and creating a fresh host permits file-only retry. These controlled-host faults do not establish natural Pi failure behavior. Hook unlink failure clears the in-flight ID first, so another hook cannot retry deletion; a later drain can use the recorded entry. Drain unlink failure ends the snapshot, and the next drain retries cleanup before continuing.

Pane sanitization keeps generated paths lexically inside a trusted root, and acknowledgement IDs must match the existing filename allowlist before hook unlink. The allowlist still accepts dotted names such as `..json` and `.hidden.json`. Neither check provides symlink-safe containment or unique pane encoding. Gap cases demonstrate pane aliases, reads through symlinked entries, and writes through symlinked ancestors. All targets stay inside the disposable fixture root. A direct local write that claims a known pane passes roster validation even with an unrelated sender ID. Roster membership is not writer authentication.

## Pi 0.84.4 compatibility

Development dependencies pin coding-agent and pi-ai to 0.84.4; consumer peer ranges remain unchanged. Every real-Pi case checks the imported project-local coding-agent, its resolved agent-core, and pi-ai metadata and prints their versions. Version drift fails rather than skips. The resource loader permits only the inline worker extension and rejects unexpected extensions, skills, prompts, themes, or context files. Only Herdr execution is replaced on the extension API. Pi owns hooks, flags, tools, custom-message delivery, and session appends.

The queue driver holds a synthetic assistant stream, publishes ordinary envelopes through the production transport, and invokes real `pi.sendMessage`. While the assistant is held, neither custom entry exists and both files remain. Releasing it lets steering consume before the earlier follow-up. Each custom `message_end` precedes its SessionManager append. `context` observes the appended entry and removes its file. The final `agent_settled` confirms both entries remain visible; reopening the actual session JSONL recovers their exact contents, details, and IDs. Text-only queue getters are not used as custom-queue evidence.

The storage cases distinguish a defined but absent session file from disabled persistence with no path. The first assistant flush writes buffered entries; later appends preserve earlier bytes. Replacing a fixture-owned session parent directory with a regular file produces `ENOTDIR` after Pi inserts the new entry into memory. Restoring the original directory before reopening proves the previous bytes survive unchanged and the failed entry is absent.

Three ordinary-message gap cases delete the only mailbox copy without a recoverable custom entry. The deferred-first-write case stops its assertions while the first assistant is held, before cleanup can append an aborted assistant. The disabled case remains without a path even after an assistant completes. The write-failed case keeps the directory fault active through Pi's real `agent_settled`, which acknowledges the memory entry; Pi reports the rejected send through its unchanged extension error bridge. These are loss-boundary observations in one process, not process-restart claims. Each gap row states the repair that would make its assertion obsolete.

The provider-error case has a narrower supported result. With persistent Pi 0.84.4 sessions, successful local writes, and retry and compaction disabled, failing the held synthetic assistant automatically consumes the queued follow-up once. Its `message_end` precedes append, `context` deletes the envelope, and a second assistant stream starts without another prompt or an intervening `agent_settled`. Reopening the actual session file recovers the exact custom entry at that boundary and after final settlement. Repeated drains do not reinject it. This does not extend to disabled or failed storage, other Pi versions, or external provider recovery.

Asynchronous send rejection remains a separate known gap. The fixture replaces only its individual session's `sendCustomMessage` method with a rejected promise, then restores it. Pi's unchanged void `pi.sendMessage` bridge reports one `send_message` extension error. No custom entry exists, and the readable envelope remains in flight through later drains even after restoration. This targeted fault injection does not claim a naturally occurring queue failure.

## Ordinary process recovery and reload

Fourteen interruption cases run the production extension and transport inside isolated controlled-host children. The sender cases use the real RPC send service with fixed Herdr responses and a listener marker, but no receiver consumes before termination. The child writes a JSON checkpoint synchronously to a dedicated inherited pipe and blocks in a finite `Atomics.wait`. The parent checks the boundary, sends `SIGKILL`, and awaits the expected exit signal before launching the replacement. No graceful shutdown hook runs in the killed process. A temporary-write wrapper writes a real 17-byte prefix before blocking; this controls a real write path without claiming an arbitrary interruption inside a kernel write.

Replacement receives paths and scenario controls only. It starts with an empty queue and injection history, reopens the surviving test JSONL, then runs the real startup drain and acknowledgement hooks. Parent checkpoint observations never populate its entries. Retry cases and the write-failed case have a previously written team record. Deferred-first-write and disabled cases keep authority only in the first host's memory and assert that no session file exists; their acknowledged envelope is also gone, so replacement has no work to validate. Replacement uses successful file-backed storage to measure recovery from what survived. Real-Pi tests independently establish the memory and write behavior behind this model.

Pre-publication interruption leaves no recoverable sender intent. Partial and complete temporary files remain ignored. After rename, parse, queue insertion, or memory insertion before write, a retained final envelope supplies a fresh delivery. The after-send case counts one injection in each process; it is retry after losing the old queue, not globally exactly-once delivery. Once the custom entry survives in the file, a replacement cleans the matching envelope without parsing its payload or injecting again. This includes interruption before acknowledgement, before unlink, and after one unlink failure. After successful deletion, recovery relies on the custom entry alone.

Three passing loss cases kill after acknowledgement with deferred, disabled, and failed message writes. Old memory contains the custom entry, but neither the envelope nor a recoverable custom entry remains. The replacement recovers no message even with working storage. Tests bound checkpoint, exit, and result waits, reject unexpected exits or incomplete pipe records, and kill and reap only fixture-owned children before deleting their root. A requested checkpoint that never arrives exercises failure cleanup as a separate fixture test.

Reload retains the host and uses reason `reload` for both shutdown and startup. A visible memory entry suppresses another injection and allows cleanup despite an absent session file. A queued payload without an entry survives replacement and receives a second injection. The actual Pi case calls `session.reload()` while the first synthetic assistant stream is held, keeps the same agent and SessionManager, and verifies old transport disposal and replacement resource isolation. Releasing successive streams consumes two custom messages with the same envelope ID; actual Pi JSONL reopening recovers two distinct session entries. The normal TUI `/reload` busy guard is outside this API-level case. Neither reload case is process-memory-loss evidence.

## Lifecycle and control recovery

Lifecycle sender cases call the real `ReportWorkerRun` tool. Sender source state and receiver authority use separate session files. Receiver tests seed registration and endpoint facts through the production registry and save team metadata through the controlled session append path. A deliberately unselected team entry and a branch view excluding lifecycle journals distinguish branch-selected live authority from all-entry accepted history. Replacement processes reopen files, then use the extension's real query server and run-query client for `get` and `replay`. Fixtures never compute run status or acceptance themselves.

Custom-message injections, report memory, reopened custom entries, raw accepted journals, live publication, replay, and deletion are counted separately. A surviving report can be accepted without another injection. A surviving accepted journal suppresses another accepted event, even when a duplicate report arrives under a different filename and causes another injection. The journal-before-publication child blocks after the host writes the journal file and before its append callback returns. No acceptor API or production pause was added. Replacement restores the exact event without historical publication, independent of which startup scan reaches the recorded report first.

Deferred and disabled report-and-journal cases acknowledge memory while no session file exists. Journal-only cases keep the previously written report and suppress later journal writes in the controlled model. The latter are not claims that a flushed Pi session defers its next append. A failed journal append retains the envelope and leaves the current acceptor at sequence zero. The two failed-write acknowledgement cases deliberately reload the extension before SIGKILL: retained journal memory restores acceptance and allows cleanup despite absent journal file recovery. The pipe records that reload separately from process-exit shutdown. SIGKILL still bypasses the exit shutdown hook, and replacement inherits no memory. This is a compound reload-then-process-loss case, not deletion directly after a thrown append.

Fail-before-memory and memory-then-file-error tests use the real handled gate and acceptor. Explicit retry follows fault removal. The controlled host writes full snapshots, so retry can recover two raw candidates but one accepted replay event. Actual Pi 0.84.4 tests induce `ENOTDIR` on the fixture-owned session directory after the custom report is written. They verify both retry and `session.reload()`, without replacing Pi append methods. Pi retains the failed raw journal in memory; retry writes only the new candidate, and later appends do not backfill the failed candidate. Reload restores memory history without live publication. Reopening actual Pi JSONL measures disk recovery separately.

Recorded malformed details, pane mismatch, duplicate event IDs, stale source sequences, protocol mismatch, and terminal conflict are handled rejections, not automatically pending work. Each rejection uses its own filename so a prior accepted custom message cannot accidentally acknowledge it. The recorded-unbound case instead keeps the file and sequence zero until saved authority is restored in a replacement host. That case reopens files in-process; it does not claim process termination.

Each control has process cases for state recovery before cleanup, write failure, and deferred/disabled state acknowledgement. Control memory-only cases start with saved state, then suppress new state writes; they measure loss of the new state change rather than a missing original session file. Controls do not inject custom messages. A retained `bind-run` creates a new source generation on redelivery, so its before-delete restart case is a known gap. A separate live-listener case waits for completed readiness renames, then re-reads the retained control and proves a second readiness publication. It does not infer publication from a timer tick. Unassigned adoption and binding retain their bootstrap exceptions. Assigned `orchestrated-by` requires a known pane, whereas `bind-run` and `released` also require the current orchestrator ID.

Uncertainty cases reopen seeded production registration, endpoint, operation-checkpoint, and acceptor records. They launch no Herdr worker. A surviving scoped uncertainty journal keeps its original event and sequence; saved registration or started history without uncertainty stays registered or started after SIGKILL. Startup adds no uncertainty or completion. The existing adapter test `shutdown during creation records uncertainty without claiming a stop` remains separate graceful-shutdown regression coverage.

## Boundary audit

The named Phase 5 boundaries map to these executing IDs. Mode suffixes below represent separate registered rows, not skipped variations.

- Sender before create, partial temporary write, before rename, and after rename: `lifecycle-before-create`, `lifecycle-partial-temp`, `lifecycle-before-rename`, `lifecycle-after-rename`.
- Receiver parse, queued handoff, and memory before write: `lifecycle-after-read`, `lifecycle-after-send`, `lifecycle-memory-before-write`.
- Recoverable report before journal and journal write before publication: `lifecycle-custom-before-journal`, `lifecycle-journal-before-publication`.
- Before deletion, after deletion, unlink failure, and duplicate filename/evidence recovery: `lifecycle-before-delete`, `lifecycle-after-delete`, `lifecycle-delete-failed`, `lifecycle-duplicate-after-restart`.
- Missing report-and-journal or journal-only writes after acknowledgement: `lifecycle-ack-report-*` and `lifecycle-ack-journal-*`, each with `deferred-first-write`, `disabled`, and `write-failed` rows. Failed-write rows include the explicit memory reload described above.
- Unbound recorded reports, pre-memory append failure, and memory-then-file failure: `lifecycle-recorded-unbound`, `lifecycle-journal-append-failed`, `lifecycle-memory-journal-error`, `pi-lifecycle-memory-journal-error`, `pi-lifecycle-memory-journal-retry`.
- Handled rejection boundaries: `lifecycle-handled-malformed-details`, `lifecycle-handled-pane-mismatch`, `lifecycle-handled-duplicate-event`, `lifecycle-handled-stale-source`, `lifecycle-handled-protocol-mismatch`, `lifecycle-handled-terminal-conflict`. Incoming unbound/unknown/stale-peer rejection remains covered by Phase 3 rows.
- Every control has `control-<action>-authority`, `control-<action>-before-delete`, `control-<action>-write-failed`, `control-<action>-ack-deferred-first-write`, and `control-<action>-ack-disabled`, for `orchestrated-by`, `bind-run`, and `released`. `control-bind-run-redelivery-ready` adds completed readiness publication on duplicate processing.
- Surviving and absent uncertainty: `lifecycle-uncertainty-survives`, `lifecycle-no-inferred-uncertainty-registered`, `lifecycle-no-inferred-uncertainty-started`.

The ordinary boundary matrix, retained-queue reload, scheduling races, and lexical/hostile-filesystem cases from earlier phases remain enabled. No producer FIFO, receiver exclusivity, writer authentication, exactly-once external execution, automatic uncertainty inference, or power-loss guarantee is added. The native watcher timeout remains unresolved; passing later runs does not close it.
