# A10: Reject a cron schedule without a prompt

## Status and decision

Specification only. This finding changes `/loop` command routing, not scheduler behavior. A complete five-field cron expression without a following prompt must produce a warning and return without creating or activating any controller. Incomplete `event` and `when` command forms must also return usage guidance instead of becoming dynamic goals.

There are no hard dependencies on the other audit fixes. Implementation should remain small and use the existing cron validator.

## Problem and evidence

`/loop 0 9 * * 1-5` currently creates a dynamic controller whose goal is `0 9 * * 1-5`. The user supplied a schedule but no work to perform. Treating that as a goal spends a controller slot and, in the real extension, requests an immediate model wake. Depending on the response, the model can continue doing work the user never described.

The evidence has different strengths:

- `docs/audits/2026-09-20-live-extension.md`, finding A10, records a deterministic reproduction only. The audit deliberately did not run this malformed command against a live model.
- `tests/extensions/audit-loop-monitor.test.ts`, test `Known audit gap: cron without a prompt is interpreted as a dynamic goal`, invokes the registered command and asserts that the first stored entry has trigger type `dynamic`. This proves incorrect routing and creation. That fixture supplies no activation callback, so it does not itself demonstrate a queued model turn.
- The retained `docs/audits/2026-09-20-evidence.json` contains selected live requests, recovery snapshots, and other results, but no A10 slash-command request. Its `dynamic-resume-update`, `dynamic-double-update`, and `dynamic-pause-state` records concern A08/A09, not proof of this malformed command firing.
- Source tracing establishes the activation consequence. `dynamicLoop()` invokes `onDynamicLoopActivated`; `loop/index.ts` wires that callback to `onLoopFire()`, which updates the controller and emits `loop:fire`. The notification runtime handles that event and can deliver a message with `triggerTurn: true`, or queue it until delivery is permitted. Do not claim that every UI state delivers immediately.

Specification review used checkout `3b2af2d`. The audit describes its earlier baseline as `1643689`. The relevant production routing still matches the audit. A bounded reproduction during specification ran:

```sh
node --import tsx --test --test-name-pattern='cron without a prompt' tests/extensions/audit-loop-monitor.test.ts
```

It passed one test, confirming the defect remains. This is not acceptance evidence for a fix.

## Scope and compatibility

In scope:

1. Recognize exactly five cron-shaped fields even without a sixth word.
2. Distinguish an invalid five-field expression from a valid expression missing its prompt.
3. Reject incomplete reserved event forms with useful guidance.
4. Prove rejection has no controller, persistence, subscription, widget, or activation side effects.
5. Document the command grammar and convert the A10 broken-behavior assertion into a positive regression.

Preserve these contracts:

- Empty input opens the existing menu. Cancelling a menu or input creates nothing.
- A valid five-field schedule followed by nonempty text still creates a recurring cron controller capped at 25 wakes. Existing whitespace normalization of the schedule and full-cron prompt remains unchanged.
- Shorthand such as `5m check the deploy` retains its existing parsing and cadence. Bare `5m` retains its missing-prompt warning.
- Complete `event <source> <prompt>` and case-insensitive `when <source> <prompt>` remain event commands, with the existing source/prompt interpretation and 25-wake cap.
- Ordinary prose remains a dynamic goal capped at 20 wakes and still activates once at creation.
- Headless `/loop` still throws `/loop requires a UI; use LoopCreate in headless mode.` before routing or state mutation.
- `LoopCreate` tool schemas, return formats, caps, and idle-trigger behavior do not change.
- Scheduled creation rollback, pause/delete/resume, expiry, read-only gates, and restoration behavior remain unchanged.

Non-goals include cron dialect changes, interval rounding, hybrid grammar, generic natural-language intent detection, six/seven-field cron support, shell-style quoting, event source allowlists, scheduler recovery, wake acknowledgement, and cleanup of old accidental goals. Do not add a model classifier or ask the model whether input looks like a schedule.

## Recommended design

### Routing order and exact behavior

Keep `parseLoopCommandRoute()` private and pure. Exercise it through the registered command rather than exporting a new API solely for tests.

Use this routing order:

1. Trim the argument. Empty input returns `menu`.
2. Keep the current complete-event match and return `event` for matches.
3. If the input starts with the whole reserved token `event` or `when`, case-insensitively, followed by whitespace or end-of-input, but did not match a complete event command, return a new `invalid-event-command` route. The handler emits warning text `Provide an event source and prompt, e.g., /loop event tool_execution_end review that tool` and returns. No interactive input dialog is opened. This also fails safely for malformed event text the existing complete-event regex cannot parse, without silently creating a dynamic goal.
4. Split trimmed input on whitespace. When there are at least five fields, inspect the first five with the current cron-shape predicate, `^[\d*/,-]+$` per field. If all five are cron-shaped, join them with single spaces and call `isValidCronExpression()`.
   - If invalid, return the existing `invalid-cron` route, even when no prompt follows. The handler keeps `Invalid cron expression: <normalized expression>` at error severity.
   - If valid and there are exactly five fields, return the existing `missing-interval-prompt` route.
   - If valid and there are more fields, return the existing cron route with `notifyEvery: false` and the remaining fields joined as today.
5. Keep existing shorthand recognition, including its missing-prompt handling and `notifyEvery: true`.
6. Otherwise return the existing dynamic route with the trimmed goal.

Use a single missing-schedule-prompt warning for full cron and shorthand. Recommended exact text is `Provide a prompt after the interval or cron expression, e.g., /loop 5m check the deploy or /loop 0 9 * * 1-5 check the deploy`. Tests should assert severity and actionable text; they need not duplicate the whole message in every case.

Validation precedence matters. `60 9 * * 1-5` without a prompt is an invalid expression, not merely a missing prompt. `0 0 31 2 *` is syntactically valid under the current validator, so without a prompt it gets the missing-prompt warning without performing a next-fire search. Once a prompt is supplied, schedulability remains the existing creation path's responsibility and overlaps A03/A06.

### Explicit ambiguity boundaries

- Exactly five numeric/cron-shaped tokens are reserved for schedules. A user who really wants a numeric-string goal can use the explicit `LoopCreate` idle form with that prompt, or add ordinary prose before the string.
- `event` and `when` are reserved only as whole first tokens. `eventually finish the release`, `whenever ready`, and `review event audit:test` remain dynamic goals. Bare `when` or `when ready` now receives guidance rather than creating a goal. This is intentional and must be documented.
- Fewer than five cron-looking fields retain the existing fallback behavior. Do not broaden A10 into a partial-cron detector that mistakes short numeric prose for a schedule.
- Named fields such as `MON`, aliases such as `@daily`, and six-field cron are not newly supported or newly classified. The existing five-field grammar is unchanged. In particular, a sixth numeric token following five valid fields is still prompt text, not a seconds/year field.
- Existing valid event matching stays first; do not alter source casing or broaden event validation into checking that a listener exists.

### Side effects, errors, and cancellation

For a missing prompt, invalid cron, or invalid reserved event form, only `ui.notify()` is allowed. Do not call `getStore().create()`, trigger add/remove, `updateWidget()`, `onDynamicLoopActivated()`, UI input/select, or persistence hooks. Do not allocate an ID and roll it back. Preserve the entire prior store snapshot, including `nextId`.

Keep the current handler's error boundary and the current scheduled-creation rollback. No new asynchronous work is needed for classification. Notification failure must not cause a fallback into dynamic creation. There is no new controller to cancel after rejection; the user can dismiss the warning or resubmit with a prompt. Existing interactive menu cancellation stays unchanged.

### API, persistence, and restoration

No public API, tool schema, persisted schema, session-log version, or file format changes are required. The only new type is a private routing-union member for malformed event commands.

Do not migrate, pause, or delete existing controllers based on a cron-looking `dynamic.goal`. An old goal may have been intentional, and persisted entries do not establish that it came from this typo. Existing entries restore exactly as before. Users can inspect and explicitly pause/delete an accidental controller with existing controls.

An invalid new command produces no new snapshot or pending notification. After restoring the before-command snapshot into a fresh in-memory store, the controller set and next ID must be identical. This is a narrow recovery assertion, not a new durability guarantee.

### Alternatives rejected

- Changing only `> 5` to `>= 5` without a missing-prompt branch can create a cron controller with an empty prompt. Add the explicit branch.
- Scheduling an empty prompt or substituting a default task invents work the user did not request.
- Opening `ui.input()` for missing arguments adds cancellation and asynchronous state behavior to a path where shorthand already returns a warning. Keep rejection and explicit resubmission consistent.
- Rejecting every five-word input would break ordinary dynamic goals. Retain the cron-shape predicate.
- Changing `LoopStore.create()` to reject cron-looking dynamic goals would interfere with explicit idle goals and saved-state compatibility. Fix the command boundary that lost the user's intent.

## Risks and review questions

| Question or risk | Recommended resolution |
| --- | --- |
| Will reserving `when` reject a previously accepted short goal? | Yes, deliberately for incomplete event syntax. Complete forms already treat it as a command prefix. Document the change and preserve non-token prefixes such as `whenever`. |
| Should an invalid five-field expression ask for a prompt first? | No. Validate syntax first and retain the invalid-cron error. |
| Should a missing prompt open an editor? | No. Warn and return, matching shorthand behavior and avoiding new asynchronous cancellation paths. |
| Should existing accidental goals be auto-cleaned? | No. There is no reliable persisted provenance distinguishing typo from intentional goal. Require explicit user cleanup. |
| Should partial schedules, named days, or aliases be rejected too? | Not in A10. This change has a precise numeric five-field boundary. Broader intent detection needs a separate grammar decision. |
| Can zero entries alone prove there was no wake? | No. Require activation, registration, persistence, and widget spies plus snapshot equality. A create/delete rollback could otherwise hide a transient side effect. |
| Does a passing full suite exclude all regressions? | No. Report the tested matrix and known audit gaps. Avoid universal reliability claims. |

No actual blocker was found in source or available tests.
