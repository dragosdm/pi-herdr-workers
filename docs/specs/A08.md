# A08: Once-per-wake dynamic update acknowledgement

## Status and decision

Specification only. This document does not change production behavior.

Require an explicit `wakeId` on `LoopUpdate`. Create and persist one opaque token when an ordinary dynamic loop records a wake. Accept one update carrying that token, then consume it in the same locked store mutation as the update. Reject missing, duplicate, stale and wrong-loop tokens without changing the controller. Keep administrative resume in the existing `/loop` menu; `LoopUpdate(status: "continue")` must no longer resume a paused controller.

This is at-most-one accepted acknowledgement per recorded wake, not exactly-once model execution or power-loss durability.

## Problem and verified evidence

The tool promises "exactly once after each wake", but the implementation currently accepts updates without a pending wake. A repeated call can overwrite the checkpoint, advance the iteration and change the next wake time. An older response can also overwrite a newer iteration. The optimistic state comparison only compares the state read at the start of the current call; it does not identify the wake being acknowledged.

## Scope and preserved contracts

In scope:

- Ordinary dynamic controllers, including idle loops created through the tool and dynamic goals created through `/loop`.
- Token creation, propagation, comparison and consumption; direct tool-call validation; restore of pending acknowledgements.
- Administrative pause/resume and final fire-cap behavior needed to prevent stale acknowledgements.
- Targeted regression tests and updated user-facing instructions.

Explicit non-goals:

- A09's checkpoint-field merge on pause. A08 changes pause acknowledgement eligibility and token consumption, not whether newly supplied pause state/metrics/done criteria reach the checkpoint.
- A11's scheduler expiry ordering, A03's creation rollback, or any cron/interval/hybrid parsing fix.
- Worker readiness, monitors, task backlog, workflows, orchestration semantics or a new LoopResume tool.
- Exactly-once message delivery, cancelling already-running model/tool work, cross-host locking, authenticated tokens, or a transaction across Pi's session log and an external side effect.
- Replacing the generic store persistence layer or changing notification delivery keys.

Preserve:

- Tool names and the three update statuses. `wakeId` is a deliberate required-input contract change, described below.
- Continue increments `dynamic.iteration` once. Pause retains the existing iteration value; completion deletes the controller. `fireCount` changes only on dispatch, never on acknowledgement or administrative resume.
- Continue preserves omitted checkpoint fields, and omitted `nextInterval` means idle-driven continuation. Existing positive-duration, seven-day, remaining-lifetime and fire-cap limits remain.
- A final recorded wake at the fire cap can still be acknowledged as paused or completed. Continue cannot renew the budget.
- Default scopes, 25-controller cap, read-only loop bookkeeping, first-wake behavior, session isolation, and no wake replay on reload.
- Workflow and orchestration-owned entries remain rejected by `LoopUpdate`, even though they use dynamic trigger/state structures internally.

## Recommended design

### 1. Token and public schema

Add `pendingWakeId?: string` to `DynamicLoopState`. Keep `awaitingUpdate` for existing presentation and restoration. For a new ordinary dynamic controller, both are absent/false until a wake is recorded. For a pending new-format wake, `awaitingUpdate === true` and `pendingWakeId` is present.

Use `randomUUID()` from `node:crypto` to mint new tokens. Do not derive new wake tokens from timestamps, iteration or fire count. Loop IDs can repeat in separate stores, and wall-clock timestamps can repeat in one process. UUIDs avoid both problems without a new counter protocol.

Add required `wakeId: Type.String({ minLength: 1, maxLength: 128, pattern: "^\\S+$", ... })` to the `LoopUpdate` schema and to `LoopUpdateParams`. Validate it again in `execute`, because adapters can bypass schema validation. Accept an opaque nonempty string of at most 128 characters with no whitespace; do not trim or coerce it. Validate `status` against the three supported values rather than allowing an unknown status to fall through to pause. Do not silently infer a token from the current controller when the caller omits it.

The wake message must include:

```text
Wake ID: <pendingWakeId>
Call LoopUpdate with id="<loopId>" and wakeId="<pendingWakeId>" exactly once for this wake.
```

Keep the existing continue/completed/paused instructions and cap warning. The `dynamic` object in pending notifications and `pi-loop` message details carries the same `pendingWakeId`; building or delivering a message must never mint a new token.

`LoopList` must display `awaitingUpdate: true` and `wakeId: <token>` for pending ordinary dynamic entries, including capped paused ones. Do not truncate this token out of the tool's text content. This allows recovery when a previously delivered wake predates the schema update. Tool errors should tell the caller to inspect the saved checkpoint, not automatically take the current token and resubmit old work.

Tokens are correlation values, not secrets or authorization credentials. Supplying the newest token from `LoopList` is an explicit recovery action and cannot establish that old external work is still relevant.

### 2. Record a wake atomically

Add a dedicated store method, recommended name `beginDynamicWake(id)`, for ordinary dynamic dispatch. Under one `withLock` operation:

1. Reload and require an ordinary dynamic entry with active status, an unexpired lifetime, remaining fire budget and no awaiting update/token.
2. Generate the UUID only after eligibility succeeds.
3. Record the fire count increment and set `awaitingUpdate: true`, `pendingWakeId`, `nextWakeAt: undefined`, and `lastUpdatedAt` using one captured timestamp.
4. If this is the final allowed fire, set the existing controller-limit pause with reason `fire cap reached`, but retain the new pending token.
5. Persist one complete controller snapshot and return the resulting entry. Rejected admission returns no entry and makes no mutation.

This can apply multiple pure reducer events inside one `withLock`, but there must not be an observable saved state with the incremented fire count and no corresponding token. Add explicit token handling to the reducer; its current hand-written dynamic merge would otherwise drop a new field.

Use `beginDynamicWake` in `onLoopFire` only for ordinary dynamic entries, excluding workflow/orchestration-owned paths. Emit/queue the wake only after this call succeeds. Do not run the old `fire` plus `updateDynamic` sequence for those entries. Two dispatch attempts while a token is pending must produce one recorded wake. Preserve existing cron/event/workflow paths.

A crash after saving a token but before queueing the notification leaves an awaiting controller, not an automatically repeated wake. Recovery through `LoopList` or explicit pause/resume remains the safe choice. This specification does not add a transactional outbox.

### 3. Accept and consume an acknowledgement under the store lock

Keep `continueDynamic` and `stopDynamic` as the adapters' entry points, but make the expected wake identity mandatory in their signatures. Remove implicit resume from `continueDynamic`. Share one internal eligibility check, so stop cannot bypass the fence. Keep current-state comparisons as supplemental checks if useful; they cannot replace the token.

The authoritative store checks, after its locked reload, must require:

- The entry exists, is an ordinary dynamic controller, and is not expired at the captured acceptance time.
- `awaitingUpdate === true` and `pendingWakeId === supplied wakeId`.
- Active status, except the final-cap acknowledgement case below.
- For continue, remaining fire budget and a valid next wake before `expiresAt`.

Validate input and next-interval parsing before mutation. Recheck lifetime, status and budget inside the lock; a preflight `get` is not authoritative in shared-file mode. Do not trust caller-supplied iteration or fields to decide token eligibility.

On success:

| Status | Authoritative mutation |
| --- | --- |
| `continue` | Apply current checkpoint merge semantics; increment iteration exactly once; clear token and awaiting flag; set next wake and update time; remain active. Re-arm only after persistence succeeds. |
| `paused` | Apply current pause semantics; clear token and awaiting flag in the same locked mutation; remain/become paused; remove scheduling. A09 separately owns merging newly supplied checkpoint fields. |
| `completed` | Delete the controller under the same checked mutation; remove scheduling. No completed-token tombstone is required. A retry after deletion returns not found. |

Use explicit property-presence semantics to clear `pendingWakeId` in `LOOP_DYNAMIC_UPDATED`, analogous to `nextWakeAt`. A nullish-coalescing merge must not retain a consumed token.

Reject duplicates even if their payload matches the original exactly. This keeps behavior simple and testable: one successful acknowledgement, followed by an explicit rejection and no state change. A delayed token from wake A must also be rejected while wake B is pending. The rejection must leave B's token usable.

A rejection must not change checkpoint, prompt, iteration, fire count, status, timestamps, next wake, timers, trigger subscriptions, pending token, snapshots or accepted-update audit entries. Return the existing tool error convention. `textResult` with `tone: "error"` throws in `loop/tools/tool-result.ts`; direct-adapter tests should assert rejection, not a fulfilled error-shaped result. Recommended diagnostic phrases are `wakeId is required`, `not awaiting an update`, `stale wakeId`, `paused; use /loop to resume`, and existing lifetime/fire-cap explanations.

### 4. Administrative actions and final fire cap

Normal `LoopUpdate` calls never resume an administratively paused loop. `/loop` Resume remains the explicit action. It clears any pending token and awaiting flag, preserves checkpoint/iteration/fire count, and retains existing lifetime/cap checks. The next actual dispatch receives a fresh UUID. It does not count resume as an acknowledged iteration.

Administrative pause through `/loop` or `LoopDelete(action: "pause")` invalidates any pending token. This must also work when an entry is already paused due to its fire cap; the current early-return in `LoopStore.pause` must not leave a token alive after an explicit administrative cancellation. Delete and expiry remove the token with the entry, or clear it if the controller is retained paused.

One exception preserves the existing final-wake contract. An unexpired entry paused with `pause.kind === "controller_limit"`, at its fire cap, and with an outstanding token from that final dispatch can accept `paused` or `completed` for that token. It cannot accept `continue`. Fire-cap retirement must preserve that outstanding token; administrative pause and expiry must not. Use an explicit internal retirement cause, `fire_cap` or `one_shot`, to distinguish this from expiry rather than retaining tokens for every controller-limit pause. Cover both `onLoopFire` and `CronScheduler.retire` so a second retirement does not invalidate the legitimate final acknowledgement.

The scheduler also calls `retire` for `recurring: false`. Preserve its pending token and allow the same paused/completed acknowledgement for an unexpired one-shot dynamic wake retired by that path, even when `maxFires` has not been reached. Do not change when one-shot retirement occurs in A08. A continue against an already retired one-shot remains a paused-controller rejection; explicit administrative resume retains existing lifetime/budget rules.

Do not cancel in-flight model turns or remove historical messages. Old messages may still be visible after administrative cancellation, but their updates must be rejected. Transport-side stale-message filtering is not necessary for A08 and must not weaken the store check.

### 5. Persistence and migration

No new snapshot log name or envelope version is needed. Add the optional dynamic field to the existing `LoopStoreData` snapshots and pending notification data. `herdr-loops.update.v1` accepted-update audit entries will include the supplied `wakeId`; restoration continues to use controller snapshots, not replay that audit log.

For new-format pending state, restore the exact saved token. Never mint a replacement on `session_start`, `/reload`, `/tree`, message retry or `LoopList`. Accepted state restores without a token; replaying the accepted call is rejected. Keep session IDs and explicit shared-file scope rules unchanged.

Legacy snapshots have no token. Normalize only ordinary dynamic entries as follows:

- Not awaiting: leave token absent.
- Awaiting and active, or awaiting and paused by final fire-cap/one-shot retirement: derive a stable migration token `legacy-<sha256>` from JSON encoding of `[id, createdAt, fireCount ?? 0, dynamic.iteration, dynamic.lastUpdatedAt ?? updatedAt]`. Use the full hexadecimal digest. Do not include fields that `LoopList` or unrelated normalization can change.
- Administratively paused: clear awaiting state and leave no token. The operator must explicitly resume rather than submit an old acknowledgement.

Derive migration tokens in `normalizeLoopEntry`, so memory/session and shared-file restore agree. Derivation must be deterministic across repeated loads and two store instances. Do not write during inspection merely to create a token. The next successful mutation persists normalized state through the existing store mechanism. This preserves the ability to inspect and acknowledge an old awaiting wake without inventing or re-running work.

A legacy wake message lacks `wakeId`. Its tokenless call is rejected with recovery guidance to inspect `LoopList`. Do not rewrite old messages or silently make their updates eligible. Recovered pending legacy messages should likewise instruct inspection when the token is absent; do not print `undefined` as a usable token.

Treat malformed new token values or inconsistent token/awaiting combinations as ineligible for acknowledgement and dispatch. Show an inspect/pause-resume diagnostic. Do not turn a malformed A08 field in one controller into a new global restoration failure. Keep unrelated legacy controllers readable. An explicit administrative pause/resume repairs the ordinary dynamic pending state without replaying an acknowledgement. Old code loading new snapshots is not a supported mixed-writer configuration; document upgrading all writers of a shared file together.

### 6. Failure boundaries

- Input errors and stale tokens do not consume the pending token. A corrected update with the same still-current token can succeed.
- Persistence failure before commit must not report success or re-arm. In memory/session mode, rely on and test `withLock` rollback when `onChange` throws.
- A shared-file write can succeed before a session audit mirror fails. A later rejected retry is safer than applying the update twice. Inspect the authoritative file/controller; do not restore the token just because the tool did not return success.
- `herdr-loops.update.v1` is appended after the authoritative controller mutation. Failure of this auxiliary append does not authorize another acknowledgement or reverse a completed mutation. Document that inspection is required after ambiguous errors.
- If trigger re-registration fails after a successful continue, do not re-open the token. The saved next-wake state is authoritative; reload/re-arm through normal recovery. Do not add a broad scheduling transaction fix here.
- Expiry is checked at acceptance, even before A11 fixes scheduler cleanup. An expired controller cannot be advanced by `LoopUpdate`.

## Alternatives rejected

- Checking only `awaitingUpdate` prevents an immediate second call but lets a delayed response for A acknowledge B.
- Using the tool-call ID only deduplicates transport retries, not two distinct calls for one wake.
- Using `updatedAt` or iteration as the wake ID repeats the current state-comparison mistake and is fragile under equal timestamps and administrative actions.
- Automatically binding tokenless legacy calls to the newest pending wake defeats stale-response rejection.
- Returning success for duplicate payloads requires retained receipts and payload comparison. A clear rejection is sufficient for the existing contract.
- Adding resume to `LoopUpdate` makes iteration acknowledgement ambiguous again. The existing menu is the supported administrative path.

## Risks and review decisions

| Question or risk | Recommended resolution |
| --- | --- |
| Is a required token too disruptive? | Accept the intentional safety-related schema change. Update wake instructions, README and `LoopList` in the same commit. No tokenless fallback. |
| Can a paused capped wake still finish? | Yes, only its retained pending token can pause/complete before expiry. Explicit administrative cancellation invalidates it. Test this before merging. |
| Should every acknowledgement increment iteration? | No. Preserve existing continue-only increment semantics in A08; changing iteration meaning is unnecessary scope. |
| Can inspection or restore rotate tokens? | No. UUID only at dispatch; stable deterministic migration only for legacy awaiting state. |
| Does a token prove the model ran the right work? | No. It correlates one update to one wake in a trusted local controller. Inspection/recovery still needs judgment. |
| What if a message is delivered twice or survives cancellation? | Both copies carry the old token; only one acknowledgement can commit, and cancelled tokens reject. Message exactly-once delivery is outside scope. |
| What if file save succeeds but journal/audit append fails? | Inspect the authoritative snapshot. Never retry by silently choosing the newest token; no cross-storage transaction is promised. |
| Could malformed token migration poison recovery? | Validate eligibility locally and fail closed for that controller without throwing a new store-wide deserialization error. |
| Should A09 be folded into this patch? | No. Define the shared checked transition now; stack A09's checkpoint merge on it. |

No actual blocker was found. Review must explicitly approve the required-input change and the final-cap exception before implementation merges.

## Definition of done

- [ ] New ordinary dynamic wake admission persists fire count and one token together before emission.
- [ ] Schema, direct adapters, messages and `LoopList` agree on required `wakeId` semantics.
- [ ] Current token succeeds once; duplicate and stale tokens cannot change counters, checkpoint, status, schedule or audit history.
- [ ] Store-lock checks protect all three statuses and two readers of the shared file, not just sequential calls in one tool fixture.
- [ ] Pause/delete/resume invalidate prior tokens appropriately; the final-cap pause/completion exception remains usable without renewing the budget.
- [ ] Reload retains pending identity without rerunning work; legacy migration is deterministic and documented.
- [ ] Persistence failures and ambiguous post-commit failures have tested, documented behavior without falsely promising exactly-once durability.
- [ ] `tests/extensions/loop-dynamic-ack.test.ts` passes positive regression cases; the original A08 known-gap assertion is replaced with desired behavior, not removed.
- [ ] Unrelated audit coverage remains; A09/A11 setup changes do not masquerade as fixes for their assertions.
- [ ] README/tool instructions explain tokens, recovery and explicit administrative resume.
- [ ] `npm run typecheck`, full `npm test`, and `git diff --check` pass in the implementation worktree after the final rebase.
- [ ] Diff review confirms no unrelated production changes, dependencies, package-lock churn or unexplained test removals.
- [ ] A focused implementation commit and reviewed PR include commands, counts/results, baseline reproduction, recovery/concurrency evidence, compatibility note and any stacked PR base.

Passing a characterization of the old broken behavior is not done. These checks establish the stated boundary; they do not prove that every possible regression or storage failure is excluded.
