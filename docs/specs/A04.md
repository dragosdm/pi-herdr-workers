# A04: preserve fresh-worker readiness during startup

## Status and decision

Specification only. This document does not implement the fix.

Retain a valid readiness envelope while its exact, parent-authorized fresh spawn is awaiting `herdr agent start`. Retry it after the parent has persisted the worker relationship and installed the lifecycle binding. Keep normal peer validation and lifecycle acceptance unchanged. Do not solve this with a startup delay, a fabricated readiness event, or a general exception for unknown senders.

The guarantee is one accepted readiness event for a successfully bound fresh spawn whose valid readiness envelope reached the parent during startup, under the existing single-receiver and successful-storage assumptions. It is not exactly-once custom-message injection across reloads or a guarantee against process death before relationship persistence.

## Problem and evidence

A child can publish readiness before the parent recognizes it as a worker. The parent currently treats that report as an unauthorized or unbound message. The mailbox then deletes the file. A later completion remains valid, but run queries retain `readiness: "unconfirmed"` and subscribers never receive the useful readiness observation.

### Measured facts versus explanation

- `docs/audits/2026-09-20-live-extension.md`, A04, reports six fresh launches with unconfirmed readiness, no accepted initial readiness, and later terminal reports using worker `sourceSequence: 2`. Re-adoption confirmed readiness.
- The portable JSON contains a narrower direct example. In `docs/audits/2026-09-20-evidence.json`, `selectedRequests` entry `runs-completed`, lines 156–190 at the audited baseline, run `188ca470-3e8c-4e6d-aeaf-a46c1ea4ccf6` has `status: "completed"`, `acceptedSequence: 2`, `orchestrationGradeCompletion: true`, and `readiness: "unconfirmed"`.
- Entry `readopt-right`, lines 221–242, retains the successful re-adoption response for run `40276dd4-330c-49a8-b5e2-0b5e8895a0a5` in the same pane. That selected response does not itself include its readiness event. The confirmed readiness and six-launch count are observations in the audit narrative, not six separately retained JSON traces.
- `acceptedSequence: 2` and worker `sourceSequence: 2` are different counters. Do not infer one from the other.
- The exact live arrival ordering was not instrumented. Source establishes a possible loss path; the proposed deterministic test must demonstrate that path. Do not claim this proves the cause of every live loss.

## Scope and compatibility

In scope:

- A fresh spawn's readiness file arriving before provider start returns or before parent relationship persistence/binding completes.
- A non-destructive mailbox delivery disposition for this temporary condition.
- A bounded retry scan after binding, including collision with an already-running drain.
- Deterministic rejection, retry, cleanup, and restoration tests.

Explicit non-goals:

- General reliable messaging, source FIFO, mailbox authentication, symlink protection, filename collisions, multi-receiver exclusivity, or acknowledgement durability.
- Retrying child readiness when no parent listener exists or the child's publication itself failed.
- Idempotent `bind-run`, changing re-adoption, or inventing uncertainty after abrupt process death.
- Accepting early ordinary messages or terminal reports before a fresh relationship exists.
- Fixing tool cancellation propagation, provider discovery, model defaults, monitor shell readiness, or any loop finding.
- Making successful spawn wait for model execution, a readiness acknowledgement, or worker completion.

Contracts to preserve:

1. Tool and RPC inputs, outputs, flags, protocol versions, lifecycle schemas, and journal formats remain unchanged.
2. Registration precedes external side effects; endpoint persistence precedes agent start. Relationship persistence remains after successful start.
3. Provider start is unconfirmed evidence. Only an actual worker readiness report confirms readiness.
4. Lifecycle reports still go through the custom-message persistence/acknowledgement gate. The retry path must not call the lifecycle acceptor directly.
5. Event identity, worker source identity/sequence, accepted ordering, canonical-before-projection publication, and terminal transition rules remain unchanged.
6. Unknown or stale peers and mismatched run/pane/protocol reports do not acquire trust through the retry path.
7. Completion remains valid without readiness. Do not reject terminal reports solely because readiness is unconfirmed.
8. The trusted-local-mailbox-root assumption remains. Matching a claimed pane is not authentication against hostile local writers.
9. Creation stays serialized through `createQueue`. Existing operation errors, uncertainty classification, retained panes, and caller-abort behavior remain intact.

## Recommended design

### 1. Add an explicit retry disposition

In `mailbox/transport.ts`, export an internal TypeScript result type:

```ts
type MailboxDeliveryDisposition = void | "retry";
```

Change `MailboxCallbacks.deliver` to return `Promise<MailboxDeliveryDisposition>`. Existing void callbacks retain their meaning. Update the extension's `HerdrWorkerTestOptions.onInboxHandler` signature and test wrappers that forward this callback.

After parsing an envelope, inspect the delivery result. For `"retry"`:

- Leave the same final file untouched.
- Do not add the filename to `inFlightEnvelopes`.
- Do not create an acknowledgement or invoke Pi.
- Continue to other files in this snapshot. One pending startup must not block established workers.
- Retry only on a later scan. Do not spin inside the current scan and do not introduce a per-file timer.

All existing void-return cleanup, marked-in-flight retention, parse-error retention, exception handling, and acknowledgement behavior stay unchanged. This is an internal callback API extension, not a wire or persisted schema change.

Important implementation detail: `tests/support/mailbox-fixture.ts` currently awaits `callbacks.deliver()` without returning its result. Change forwarding wrappers to preserve the disposition and update their promise types. Otherwise a correct extension will still delete the file in integration tests.

### 2. Classify authorized startup readiness before normal peer rejection

Add a small predicate in `extensions/herdr-worker.ts`, near `deliver()`. Return `"retry"` before `knownPeerPanes()` only when all of these conditions hold:

- The envelope passes existing sender-shape checks and `isWorkerRunReport()`.
- It is a lifecycle report with `status: "started"` and `evidence.kind: "worker_ready"`.
- `pendingSpawnLifecycles.get(report.runId)` exists, identifies a fresh spawn awaiting its relationship/binding, and has a concrete pane ID.
- Claimed sender pane exactly equals that pending pane, and report protocol equals the pending run's selected lifecycle protocol.
- The provider is interactive and not stopped.

Use a dedicated optional boolean on `PendingSpawnLifecycle`, named `awaitingReadinessBinding`, rather than inferring eligibility from `scope` alone. Set it for the fresh-start entry before issuing `agent start`. Do not set it for re-adoption or assignment delivery. `scope` remains the uncertainty classification and must not be overloaded.

The parent-generated run ID and exact created pane are mandatory. A name match alone, an arbitrary registered run, an endpoint journal alone, or an unknown report that merely says it is ready is insufficient. Preserve the existing sender-ID trust model; do not add a new name-alias authentication rule in this fix.

This predicate grants permission to retain a file, not permission to accept its contents. When retried after startup, the envelope must pass the unchanged live peer and run/pane checks. Invalid shapes, wrong protocols, wrong runs, wrong panes, and early non-readiness messages follow existing rejection behavior. Do not warn that a correctly deferred readiness file came from an unknown agent.

### 3. Close the gate and retry after successful startup

Preserve the existing successful fresh-start sequence through relationship persistence and `observeProviderStarted()`.

Immediately afterward:

1. Clear `awaitingReadinessBinding` for this run while retaining the pending record needed for shutdown/assignment-delivery uncertainty.
2. Request and await one mailbox scan that is guaranteed to run after any current scan finishes.
3. Continue existing initial-prompt delivery and spawn return logic. Do not wait for Pi to consume the readiness message or acknowledge it.

The normal `bindLifecycleRun()` call still happens inside `observeProviderStarted()`. If journal publication throws after binding, retry can still hand off worker readiness through the normal gate. Preserve the policy that lifecycle publication errors do not fail an otherwise successful worker creation. A persistence fault is not permission to synthesize readiness or bypass binding validation.

A plain `await mailbox.drainInbox()` is insufficient: current `drainInbox()` returns immediately when another pass is active. Add `MailboxTransport.drainInboxAfterCurrent(): Promise<void>` for this explicit synchronization point:

- If idle, run one normal snapshot scan.
- If a scan is active, queue one additional snapshot after it settles, including when it encountered an error. Multiple such requests coalesce into that additional scan.
- Resolve after the requested scan, or resolve without delivery if stopped/non-interactive.
- Keep ordinary watch/poll `drainInbox()` overlap suppression and sorted-snapshot semantics unchanged.
- No recursive unbounded rescans, new interval, or requirement that a future native watch notification occur.
- Follow existing warning/error isolation. The startup retry scan must not replace the provider operation's result with a mailbox warning.

Store only the active/queued scan promises or equivalent bookkeeping, not copies of envelopes. The existing files are the retry storage. Be careful not to make a scan await itself. This new method is called from the spawn continuation, not from `deliver()`.

This ensures an already-published early readiness file gets another delivery opportunity before the initial brief is sent, even if all native watcher notifications happened too early. It does not impose new producer FIFO guarantees on arbitrary mailbox traffic.

### 4. Failures, shutdown, and cancellation

- Pane split failure or missing pane ID never enables readiness deferral.
- Start rejection, provider timeout, or parent relationship persistence failure keeps the existing error and uncertainty outcome. Clear the pending entry/eligibility in every exit path. Do not leave permanent retry authority.
- After a failed spawn, a retained file is handled on the next ordinary scan under existing authorization rules. With no established worker relationship it is rejected and removed. Relationship persistence can throw after mutating in-memory state today; if that state and the uncertainty binding satisfy existing checks, later genuine readiness may still be accepted normally. Do not add rollback semantics or a new acceptance exception in A04. The spawn error remains an error even if later worker evidence strengthens the lifecycle state.
- Graceful shutdown first preserves existing scoped uncertainty reporting, then clears pending eligibility and stops transport activity. A queued post-current scan resolves without injecting or deleting files after stop. No worker pane is terminated automatically.
- An RPC caller abandoning its reply does not cancel an already-running provider operation today. Keep that behavior; an eventual successful binding still retries readiness. A pre-creation abort enables no pending readiness permission.
- Existing tool-signal propagation limitations remain outside A04. Tests should assert cleanup when the provider operation actually rejects or lifetime shutdown aborts it, not pretend every caller signal stops Herdr.
- Existing Pi handoff rejection and memory-before-disk acknowledgement gaps remain documented. Do not catch those errors by dropping the file or claiming acceptance.

### 5. Persistence and restoration

No new journal entry, state version, migration, or disk queue is needed. The eligibility flag is in-memory operation state; the deferred envelope stays in the existing mailbox.

- After successful relationship persistence, reload/restart rebuilds the normal binding from saved metadata. A retained readiness file follows the normal peer check and acceptance path.
- A surviving readiness custom entry can be accepted after reload without reinjection. A surviving accepted journal restores confirmed readiness without republishing historical events.
- If the parent dies before relationship persistence, the transient startup permission is gone. Restoration must not reconstruct trust from an arbitrary envelope or endpoint registration. The existing unknown/unbound rejection and uncertainty limitations apply. Document and test this fail-closed boundary rather than claiming crash-safe startup readiness.
- Old unconfirmed completed runs remain unchanged. No backfill from source-sequence gaps, no rewriting audit evidence, and no synthetic historical readiness.

### Alternatives rejected

- Extra sleep before/after `agent start`: does not establish ordering or prevent a watcher from draining early.
- Marking a deferred file in flight: ordinary drains would skip it forever without a custom entry to acknowledge.
- Throwing from delivery to mean retry: stops unrelated traffic and emits misleading warnings.
- Buffering the envelope only in memory: discards the recoverable file and creates another loss boundary.
- Retrying all unknown/unbound reports: weakens authorization and leaves arbitrary local files pending indefinitely.
- Pre-populating the worker relationship before start: changes failed-start team/inspect semantics and still depends on live roster visibility. Narrow retention avoids those compatibility changes.
- Rebinding or asking the child to emit a replacement readiness event: changes source generation/sequence semantics and can duplicate readiness.

## Test matrix

Use barriers and explicit callbacks, not timing luck. Every asynchronous wait must have a finite timeout and cleanup must release barriers in `finally`/test teardown. Do not launch real Herdr panes in automated tests.

Retry queues the original event; consume/write custom entry and acknowledge. Query and replay show confirmed readiness and one accepted worker-ready event. |

## Risks and review decisions

| Question or risk | Recommended resolution |
| --- | --- |
| Is the live cause proven? | No. Describe live symptoms and source-supported ordering separately; require deterministic loss/fix evidence from real production paths. |
| Does retaining an unknown sender weaken trust? | Permit retention only for the exact in-flight parent-created run/pane/protocol. Reapply ordinary live peer and binding checks before injection. Keep hostile local-writer limitations explicit. |
| Can a retry file remain forever? | Eligibility ends with the provider operation. No per-file timer is needed; next normal scan handles rejection after failure. Process stop leaves files for normal restoration, not permanent in-memory locks. |
| Could the retry API change ordinary snapshot tests? | Keep ordinary `drainInbox()` semantics unchanged; only the explicit new after-current method requests an additional scan. Test coalescing and disposal. |
| Could completion overtake readiness? | Run the post-binding scan before initial brief delivery for an already-published readiness file. Preserve existing follow-up ordering. Do not claim arbitrary producer FIFO or permit late readiness to weaken terminal transitions. |
| Does this fix abrupt startup death? | No. Preserve fail-closed restoration before relationship persistence and document it. Durable pending-spawn recovery is a separate protocol project. |
| Does a journal write failure change spawn success? | No. Preserve current observation-error isolation and acceptance retry assumptions. Test successful storage for the primary guarantee and retain existing storage-fault coverage. |
| Should all early lifecycle reports be retained? | No. Restrict A04 to worker readiness; other early traffic needs its own contract review. |

No current implementation blocker was found. The lack of a live scheduling trace limits causal claims, not the ability to implement and test the source-level race. Live verification requires separate pane/model authority; deterministic verification does not.

## Definition of done

- [ ] The dedicated positive regression fails on the baseline for the expected early-file deletion and passes with the fix.
- [ ] While start is held, the exact authorized readiness file survives repeated real transport scans without injection, acceptance, mutation, or an unknown-peer warning.
- [ ] Successful binding triggers a reliable post-current retry; after normal acknowledgement there is exactly one accepted original readiness event and query/replay reports confirmed readiness.
- [ ] Wrong identities, malformed reports, genuine unknown peers, and stale panes remain rejected; retention alone grants no acceptance authority.
- [ ] Start failure, timeout, relationship persistence failure, caller-abort boundaries, and shutdown clear eligibility and preserve existing errors/uncertainty without killing panes or claiming completion.
- [ ] Recovery under surviving relationship/journal state works; interrupted pre-binding startup remains fail-closed and documented.
- [ ] Re-adoption, source sequence, completion without readiness, journal/publication ordering, release, and normal message routing retain their contracts.
- [ ] Targeted new and existing worker/mailbox/lifecycle/query tests pass with the commands above. No unrelated gap coverage is removed, skipped, or relabeled to hide a failure.
- [ ] `npm run typecheck` passes.
- [ ] Full `npm test` passes after final integration, with totals and any baseline/environment issue recorded honestly.
- [ ] `git diff --check` passes.
- [ ] Lifecycle and mailbox documentation explains the retry exception and unchanged durability/security boundaries; public schemas and persistence formats remain compatible.
- [ ] Diff contains no unrelated production, package, lockfile, audit-evidence, or test changes.
- [ ] An independently reviewed implementation commit and PR include the chosen design, baseline failure evidence, passing commands/results, relevant query/replay assertions, and either bounded live evidence or an explicit statement that live smoke verification was not performed.

A passing reproduction of lost readiness is not completion. These checks establish the listed contracts and boundaries, not proof that every possible regression is excluded.
