# A06: Cron dialect semantics and bounded next-occurrence search

## Status and purpose

Specification only. No production fix is included here.

Implement a documented numeric five-field cron dialect with Unix-style day-of-month/day-of-week combination. Find sparse future occurrences without scanning every intervening minute. Keep controller lifetime separate from schedule validity.

The implementation should be based on the A03 recovery fix. A06 owns cron semantics and search, not creation transactions or quarantine policy.

## Verified problem and evidence

The audit is correct about both A06 defects.

- `loop/loop-parse.ts:126-155`, `cronToNextFire()`, requires every field to match separately. In particular, lines 148 and 150 combine day-of-month and weekday with AND.
- `loop/loop-parse.ts:8` sets `MAX_CRON_SEARCH_MINUTES` to `366 * 24 * 60`. `cronToNextFire()` throws after that limit even when a later date exists.
- `tests/extensions/audit-loop-monitor.test.ts:42-50` contains two `Known audit gap` tests that assert these broken results. They are reproductions, not acceptance tests.
- `README.md:201` advertises a five-field cron expression without describing a nonstandard day combination or a one-year search restriction.

A bounded, read-only reproduction during specification used `TZ=UTC`, Node with `--import tsx`, and the production function. From `2026-09-20T12:00:00Z`:

| Expression | Current result | Required result |
| --- | --- | --- |
| `0 0 1 * 1` | `2027-02-01T00:00:00.000Z` | `2026-09-21T00:00:00.000Z` |
| `0 0 29 2 *` | `No matching time found` | `2028-02-29T00:00:00.000Z` |

The first error can suppress all scheduled wakes during a controller's lifetime. The second labels a valid schedule as unusable and reaches A03's failed-create persistence path.

Relevant evidence in `docs/audits/2026-09-20-evidence.json` is indirect for A06. `impossible-cron` reports a scheduling exception for `0 0 31 2 *`; `loop-after-error` shows the entry still active; `poison-create`, `poison-emit`, and `poisonedReloadSnapshot` document the recovery consequence. The audit also cites `poison-event-create`, but that individual request is not retained in the selected JSON requests; the snapshot contains the event controller. There is no retained live leap-day or DOM/DOW request in that evidence file. Do not describe A06 as live-reproduced. Its evidence is deterministic tests and source inspection.

Other source contracts relevant to the fix:

- `isValidCronExpression()` and `isValidCronField()` in `loop/loop-parse.ts:63-96` validate syntax and field ranges, not calendar feasibility.
- `parseInterval()` in the same file accepts full expressions after syntax validation. Its shorthand rounding belongs to A05.
- The module-level `computeNextFire()` and `CronScheduler.armTimer()` in `loop/scheduler.ts:6-15,96-122` use the same cron function for cron, hybrid, and active workflow-state schedules. `armTimer()` already puts a controller in `expiryTimes`, with no `fireTimes` entry, when its jittered next fire is at or beyond expiry. Preserve that behavior.
- `MAX_LOOP_EXPIRY_MS` in `loop/loop-reducer.ts:6` is seven days. `LoopStore.expireEntryUnlocked()` in `loop/store.ts:609-635` deletes ordinary loops and pauses workflow/orchestration/task-backlog controllers on expiry.
- `LoopCreate.execute()` in `loop/tools/loop-tools.ts:243-295` creates before registering triggers. A03 owns making that operation safe on scheduling failure.
- `TriggerSystem.start()` in `loop/trigger-system.ts:19-27` starts the scheduler before event subscriptions. A03 owns isolation of invalid restored entries.

Line numbers describe the specification baseline; function names are the stable references.

## Scope and non-goals

In scope:

1. Specify the accepted grammar and day matching rules.
2. Correct next-occurrence results, including leap days beyond one year.
3. Keep search finite and avoid multi-year minute-by-minute traversal.
4. Define local-time gap/fold behavior and test it.
5. Verify that a valid distant occurrence becomes an expiry-only controller, including restoration and hybrid event subscriptions.
6. Document the intentional semantic correction for existing persisted expressions.

Not in scope:

- A03 rollback, recovery quarantine, or storage durability changes.
- A05 elapsed-time scheduling or shorthand normalization.
- A07 hybrid input grammar, A10 command routing, or new tool parameters.
- A08/A09 dynamic update semantics or A11 awaiting-update expiry ordering.
- New timezone selectors, `CRON_TZ`, seconds/year fields, named months/weekdays, macros, `L`, `W`, `#`, or `?`.
- Removing jitter, making delivery punctual while the agent is busy, replaying missed occurrences, extending the seven-day lifetime, or adding cron dependencies.
- Proving compatibility with every cron distribution or every historical timezone rule.

Keep the signatures and meaning of these public helpers:

```ts
isValidCronExpression(expr: string): boolean
parseInterval(input: string): { cron: string; description: string }
cronToNextFire(cronExpr: string, fromDate?: Date): Date
```

`isValidCronExpression()` remains a syntax validator. Thus `0 0 31 2 *` remains syntactically valid but has no occurrence. `cronToNextFire()` remains synchronous and throws if it cannot return a supported occurrence. No persisted type, tool schema, store version, or journal record changes are required.

## Recommended design

### 1. Define the numeric dialect

Use five whitespace-separated fields in this order: minute, hour, day-of-month, month, weekday. Ranges remain `0..59`, `0..23`, `1..31`, `1..12`, and `0..6`. Sunday is `0`; `7` remains unsupported and must be documented, rather than silently added in this fix.

Preserve currently accepted field forms:

- `*`, an unsigned decimal integer, or an ascending inclusive numeric range.
- Comma-separated unions of those forms.
- `/step` on `*` or a range, with positive integer steps no larger than that field's width, as today.
- Steps start at the field minimum for `*`, or the range's lower bound. For example, DOM `*/2` selects `1,3,5,...,31`.
- Duplicate list items and leading zeroes are accepted as today. Descending ranges, empty items, scalar steps such as `5/10`, zero steps, signs, fractions, names, and extra fields remain invalid.

Do not broaden or tighten the grammar incidentally while changing the matcher. Whitespace trimming and whitespace between fields remain supported.

Compile each field once per `cronToNextFire()` call into a small membership set or boolean array. Share the parser with validation, or otherwise keep one grammar implementation. Avoid reparsing strings for each candidate minute. There is no need for an unbounded global cache.

### 2. Combine the two day fields explicitly

Use the Vixie-style leading-star distinction. A day field is wildcard-based when its original trimmed token starts with `*`, including `*/n`. Keep this bit alongside its expanded values; do not infer it from the resulting set.

For a candidate local date:

```text
if DOM is wildcard-based OR DOW is wildcard-based:
    dayMatches = domMatches AND dowMatches
else:
    dayMatches = domMatches OR dowMatches
```

Minute, hour, and month must always match. Consequences:

- `0 0 1 * 1` runs on every first of the month and every Monday.
- `0 0 * * 1` runs on Mondays, not daily.
- `0 0 1 * *` runs on the first, not daily.
- `0 0 * * *` runs daily.
- `0 0 */2 * 1` runs on Mondays whose day number belongs to `1,3,5,...,31`.
- `0 0 1-31 * 1` uses OR because `1-31` is not wildcard-based. It runs daily. Do not canonicalize this range to `*` and change its meaning.
- Preserve token order when determining the flag. A list beginning `*,...` is wildcard-based; one beginning with a numeric item is not. Test this uncommon but accepted grammar explicitly. Document the leading-star rule so it is not an accidental parser property.
- `0 0 31 2 1` is feasible: restricted weekday permits Mondays in February even though February has no 31st. `0 0 31 2 *` is not feasible.

### 3. Bound the search without confusing it with controller expiry

Use an explicit search endpoint at the local calendar date 400 years after the starting local date, plus one local calendar day. Preserve the starting wall-clock time when constructing the endpoint. Include candidates at the endpoint. Place a defensive maximum of 146,100 local-date iterations on the search as well. One Gregorian cycle has 146,097 days; the small margin accommodates the partial starting date and endpoint.

A 400-year Gregorian cycle covers all calendar date/weekday combinations in this grammar. Eight years handles the longest simple leap-day gap, but is not sufficient for the retained wildcard-step grammar: `0 0 29 2 */7` requires February 29 to be Sunday and can wait 28 years. Do not advertise an unlimited next-occurrence service. If the search exhausts its supported horizon, report that fact rather than claiming a mathematical proof of impossibility in every timezone. Date skipping is essential to make this longer bound practical.

Recommended algorithm:

1. Parse/compile and validate the expression.
2. Reject a non-finite `fromDate` immediately. Copy its value and never mutate the caller's `Date`.
3. Construct the finite calendar horizon. If JavaScript's date range cannot represent it, throw a clear search-range error before iteration.
4. Start at the next real minute boundary strictly after `fromDate`, using epoch arithmetic: `floor(fromMs / 60000) * 60000 + 60000`. Do not use local `setMinutes()` to advance through repeated hours.
5. Examine local dates in increasing time order. Skip a date at once if its month or combined day predicate does not match. Compute local day boundaries with calendar arithmetic, not by adding 24 hours. Guard every jump against non-finite dates and non-increasing timestamps. JavaScript can normalize a nonexistent midnight or a skipped date; re-evaluate the actual resulting local date before matching it.
6. For an eligible local date, scan its real minute instants from the current cursor to the next local day boundary or horizon, whichever comes first. Compare hour/minute membership and recheck the full local fields before returning. Advancing by epoch minutes naturally visits both sides of a repeated hour. Most searches stop on their first eligible date; impossible calendar dates never incur a minute scan.
7. Return a fresh `Date` for the first match. If none is found within the horizon/date-iteration cap, throw the bounded-search diagnostic below.

Use a bounded pure helper for date iteration if it makes the implementation easier to test. No background jobs, timers, shell loops, or new package dependencies are needed. Do not merely multiply the existing minute-loop cap: impossible schedules would block startup for hundreds of millions of candidate minutes per controller.

### 4. Timezone and precision behavior

The dialect uses the host process's local timezone, as the existing implementation does. A schedule is wall-clock based, not an elapsed duration.

- The result is strictly later than `fromDate`, even when `fromDate` is already on a matching minute.
- Seconds and milliseconds on returned modern-date occurrences are zero.
- Spring-forward times that do not exist are skipped, not shifted to a different hour.
- Both real instants in a fall-back repeated local minute are eligible. Calling the helper after the first instance can return the second instance.
- Midnight transitions, non-hour offsets, and whole skipped local dates must not create a false match or a non-progressing search.
- A timezone change between sessions causes recomputation in the new host timezone. There is no persisted timezone pinning.
- The scheduler may add jitter, delay delivery while busy, or skip a missed occurrence according to existing runtime behavior. The helper's repeated-hour semantics do not promise two delivered wakes regardless of jitter and agent availability.

Tests should use modern dates and explicit `TZ` subprocesses. Do not claim exhaustive historical timezone compatibility from that matrix.

### 5. Errors and cancellation

Keep `Invalid cron expression: ...` for malformed syntax. For exhausted search, preserve the recognizable `No matching time found` prefix and add the supported horizon, for example:

```text
No matching time found within 400 years plus 1 day for cron expression: ...
```

Use clear, separate errors for an invalid start date and an unrepresentable search range. Do not return an `Invalid Date`, fake occurrence, `Infinity`, or ambiguous `undefined`.

These diagnostics do not change the synchronous API or add an abort signal. The finite date bound and date skipping provide the cancellation boundary: the helper finishes or throws without owning external resources. Existing tool and session cancellation behavior remains unchanged. Do not describe synchronous search as preemptible.

A03 must continue to remove any failed creation and isolate failed restoration. A06 must not catch an error and pretend the controller was scheduled successfully. For a valid sparse schedule, there is no error to quarantine.

### 6. Lifetime, restoration, and compatibility

A valid future schedule remains accepted even if its next occurrence is later than the controller's remaining lifetime. Do not reject it solely because no occurrence falls in the next seven days, and do not extend `expiresAt` to reach the next occurrence.

Retain `CronScheduler.armTimer()`'s existing result:

- If `nextFire + jitter < expiresAt`, arm the fire time.
- Otherwise remove any previous fire time and retain only the expiry time.
- `nextFire(id)` returns `undefined` for expiry-only controllers, as today. No new sentinel timestamp is needed.
- A hybrid controller with an expiry-only cron side still subscribes to its event side and may fire from events before expiry.
- Expiry follows the existing store disposition and `canExpire` guard. Deletion, pause, `remove()`, and `stop()` must clear timers normally.

For persisted entries, use the corrected matcher on the next restoration or re-arm. There is no legacy AND mode and no stored-expression rewrite. Existing DOM/DOW-restricted entries may next wake sooner than before; call this out in the README release/change note. Never replay older matching times or reset counters, creation times, expiry times, IDs, or paused status as a migration.

Restoring a valid leap-day entry together with an unrelated event loop must succeed, preserve the leap-day entry as expiry-only, and subscribe the event loop. Recovery of truly invalid entries remains an A03 requirement.

## Risks and review decisions

- Existing expressions with two restricted day fields will wake more often. Recommended resolution: treat this as the advertised-semantics bug fix, document it, preserve existing fire caps/lifetime, and do not add a legacy mode.
- Cron implementations differ in wildcard-step and Sunday-alias handling. Recommended resolution: publish the exact leading-star rule and the retained `0..6` numeric subset. Do not claim complete POSIX/Cronie compatibility.
- A short horizon can reject leap years around 2100 or wildcard-step day intersections. Recommended resolution: use the specified 400-year-plus-one-day endpoint and test both 2096 to 2104 and the 2032 to 2060 February-Sunday gap. Reject one-, four-, and eight-year bounds for this grammar.
- A longer horizon can freeze startup if implemented as a minute loop. Recommended resolution: compile once and skip ineligible dates. Review complexity and candidate counts, not just a fast result on one laptop.
- Local Date setters can jump backward in a fold or normalize a gap into the wrong hour. Recommended resolution: enumerate real minute instants within local day boundaries, recheck returned fields, and test non-hour and skipped-date transitions.
- Accepting a schedule that will expire without a cron wake can surprise callers. Recommended resolution: retain existing expiry-only semantics and document them. Do not extend lifetime or reject a valid schedule merely to avoid explaining the limit.
- A03 may classify all no-next-fire cases as invalid. Recommended resolution: keep a valid distant result as a `Date`; let the scheduler apply expiry. Coordinate before implementation, using the unchanged helper signature.
- Timezone database versions differ. Recommended resolution: pin explicit zones and known transition dates in tests, print zone/runtime details on failure, and avoid claiming exhaustive historic-zone coverage.
