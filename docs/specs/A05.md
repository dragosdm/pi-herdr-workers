# A05: reject unsupported interval shorthand instead of approximating it

## Status and decision

This is an implementation specification, not an implementation. Source was reviewed at checkout `3b2af2d`; the audit used baseline `1643689`.

Keep cron as the scheduling mechanism. Accept duration shorthand only when its duration exactly matches an entry in the existing `COMMON_INTERVALS` table. Reject everything else rather than rounding, including sub-minute and multi-day requests. Explain that successful shorthand requests select local wall-clock cron slots, not elapsed-time timers, and that the scheduler adds jitter.

This deliberately tightens input acceptance. It does not introduce an elapsed-time trigger, change saved controllers, or change when existing cron schedules fire.

## Problem and verified evidence

`parseInterval()` converts duration shorthand into a five-field cron expression. Today it accepts zero, rounds other inputs to a small table, and discards the requested duration. A caller can request two days and get daily wakes, or request three minutes and get two-minute wakes. This changes polling frequency and can consume more model turns than authorized.

Its `selectedRequests` entry `loops-hybrid-short` shows a valid `1h` shorthand returning only `hybrid: cron 0 * * * * + event audit:hybrid`. This corroborates the output shape, not multi-day timing. The audit's A04 readiness explanation is a source-supported race hypothesis, not an instrumented arrival trace, and is unrelated to this parser defect.

## Scope and compatibility

### In scope

- Strict validation and exact table lookup in `parseInterval()`.
- Consistent validation for tool cron creation, the cron component of currently supported hybrid syntax, slash-command scheduled creation, and the scheduled menu.
- Narrow recognition of malformed duration-like inputs so negative, decimal, exponent, and non-finite unit-suffixed forms cannot accidentally create an inferred event or dynamic loop.
- Clear errors, scheduling semantics in success output, tool parameter descriptions, and README documentation.
- Positive parser, adapter, and restoration regressions.

### Explicit non-goals

- Arbitrary elapsed-time recurring timers, sub-minute cron, new trigger types, timezone selection, or new duration units.
- New supported table cadences such as `3m` or `4m`, even where a cron expression could represent them.
- Changing cron day matching, search horizon, DST handling, jitter, runtime expiry, busy-agent delivery, or caps.
- Fixing impossible-cron persistence and recovery, A03; hybrid full-cron grammar, A07; full-cron missing-prompt routing, A10; or dynamic update semantics, A08/A09/A11.
- General natural-language schedule detection. Ordinary event names and dynamic goals remain valid.
- Modifying `LoopUpdate.nextInterval`, workflow cron validation, worker protocols, monitors, or mailbox behavior.

### Contracts to preserve

- Keep `parseInterval(input)` returning `{ cron: string; description: string }` or throwing an `Error`. Keep its five-field cron validation and pass-through behavior.
- Preserve the current exact table mappings and descriptions for accepted shorthand, including uppercase units, leading/trailing whitespace, whitespace between number and unit, and leading zeros.
- Preserve explicit `triggerType: "event"` as literal event-source intent, even when its source resembles a duration. `/loop event <source> <prompt>` remains the explicit command escape.
- Preserve `triggerType: "idle"`, ordinary event inference, dynamic goals, `recurring`, `readOnly`, `maxFires`, and existing error propagation through Pi.
- Preserve persistence shapes, snapshot/journal versions, IDs, and restoration. No schema migration or dependency change is needed.
- Keep existing cron strings accepted regardless of whether they correspond to the shorthand table. For example, explicit `*/3 * * * *` remains legal. Do not apply the shorthand table restriction to five-field cron.
- Preserve dynamic elapsed delays such as `LoopUpdate.nextInterval: "30s"`, `"3m"`, and `"2d"`, subject to its existing lifetime checks. They must not use the new cron shorthand restriction.

## Recommended design

### 1. Exact shorthand conversion

Retain the strict duration grammar `^\d+\s*[smhd]$`, case-insensitive after trimming. The broader recognition rule below is only routing, not acceptance.

After matching:

1. Convert the integer text to a number and resolve its known unit multiplier.
2. Reject if the value or total seconds is not a positive safe integer. This includes non-finite conversion or multiplication. Do this before comparing against the table.
3. Look up total seconds directly in `COMMON_INTERVALS`.
4. If missing, throw an unsupported-interval error. Do not clamp, round, choose a nearest alternative, or create a controller pending confirmation.
5. If present, return its existing cron and human-readable duration description.

Remove `roundToNearestCommon()`. Its duration-description formatting can become a small formatter for an already validated exact table key. There must be no fallback to the first or last entry.

The accepted durations are exactly:

| Duration | Cron |
| --- | --- |
| `1m` | `*/1 * * * *` |
| `2m` | `*/2 * * * *` |
| `5m` | `*/5 * * * *` |
| `10m` | `*/10 * * * *` |
| `15m` | `*/15 * * * *` |
| `30m` | `*/30 * * * *` |
| `1h` | `0 * * * *` |
| `2h` | `0 */2 * * *` |
| `3h` | `0 */3 * * *` |
| `4h` | `0 */4 * * *` |
| `6h` | `0 */6 * * *` |
| `8h` | `0 */8 * * *` |
| `12h` | `0 */12 * * *` |
| `1d` | `0 0 * * *` |

Equivalent integer-unit spellings are accepted, for example `60s`, `120s`, `60m`, `24h`, and `86400s`. `1.0h`, `+1h`, and `1e0h` remain invalid syntax even though they could describe a supported value. `0s`, `0m`, `0h`, `0d`, `1s`, `59s`, `61s`, `90s`, `3m`, `90m`, `23h`, `25h`, `2d`, and arbitrarily large durations all fail.

### 2. Prevent invalid duration routing from starting other loop types

Add an internal exported helper in `loop/loop-parse.ts`:

```ts
matchIntervalPrefix(input: string): { interval: string; rest: string } | undefined
```

It trims the input and recognizes a duration-looking prefix whose unit is followed by whitespace or end-of-input. The amount may look like a signed integer, decimal, exponent, `Infinity`, or `NaN`; the unit is exactly `s`, `m`, `h`, or `d`, case-insensitive. Recognition does not imply validity.

Use this prefix pattern, with the remainder extracted after the match and trimmed:

```text
^([+-]?(?:\d+(?:\.\d*)?|\.\d+)(?:e[+-]?\d+)?|[+-]?(?:Infinity|NaN))\s*[smhd](?=\s|$)
```

Compile it case-insensitively. Return the full matched interval text, not just the amount capture.

- `inferTriggerType()` uses this helper when no explicit type exists. A match with empty `rest` routes to cron and therefore validation. Keep existing hybrid and five-field cron inference priorities.
- `parseLoopCommandRoute()` replaces its current shorthand-prefix match with this helper. Keep event-command and full-cron handling before it. A nonempty remainder is the prompt. An empty remainder keeps the missing-interval-prompt behavior and creates nothing.
- The menu already invokes `parseInterval()` directly, so no routing change is needed there.
- Do not infer schedules from arbitrary text containing a duration later in the string. `review 3m timeout` stays a dynamic goal. `audit:1m`, `1month`, and an explicit event named `-1m` stay event inputs under their existing contracts.
- Unsupported units such as `1w` are not added to inferred duration syntax. With explicit cron intent they fail parsing; free-form inference remains unchanged.

This is a narrow A05 validation safeguard. It must not implement A10's five-field missing-prompt or event-prefix fixes.

### 3. Errors and side effects

All duration failures must occur before `getStore().create()`, trigger registration, dynamic activation, widget success updates, or snapshot writes. The helper itself is pure.

Use consistent parser error categories:

- Zero or numerically unsafe integer shorthand: `Interval must be a positive safe integer duration: "<input>".`
- Valid positive integer syntax absent from the table: `Unsupported cron interval "<input>". Supported durations: 1m, 2m, 5m, 10m, 15m, 30m, 1h, 2h, 3h, 4h, 6h, 8h, 12h, 1d. No rounding is applied; use an explicit five-field cron for a different wall-clock schedule.`
- Malformed duration syntax: retain `Cannot parse interval` and explain integer-unit shorthand or explicit cron. Do not suggest that arbitrary integer durations are supported.

Tests should assert the category and the no-creation outcome rather than every punctuation character. Bound echoed input to 120 characters plus an ellipsis for larger values; do not allocate a giant error message from an overflow test input. Existing invalid full-cron error handling is unchanged.

`LoopCreate.execute()` rejects through its existing error mechanism. `createCronLoop()` reports the parser message with UI severity `error`; it does not fall back to a dynamic goal. `textResult()` with an error tone already throws, so do not introduce a visually red success response.

No new asynchronous validation or resources are needed. Existing menu cancellation before prompt/interval submission remains a no-op. Successful controllers still cancel through existing pause/delete paths; A05 adds no cancellation token or timer lifetime.

### 4. Explain successful schedules

Keep current IDs, trigger descriptions, recurring status, and success fields. Add this timing note to cron and hybrid `LoopCreate` textual content and expanded display details, and to scheduled-command success notifications:

> Timing: local wall-clock cron with scheduler jitter, not an elapsed-time interval.

Do not add this note to event-only or idle/dynamic creation. The command must not claim an exact delay from creation. Existing short descriptions such as `5 minutes` remain useful, but must be accompanied by the timing note.

Update the `LoopCreate.trigger` parameter description to call these values "supported cron shorthand" rather than implying all intervals work. Include the accepted set in README, with examples of rejected `0m`, `30s`, `3m`, and `2d`. Document that explicit cron can express additional calendar schedules but is not a general elapsed-time fallback. Do not recommend `*/2` day-of-month as a faithful every-two-days timer.

README must distinguish dynamic `nextInterval` from recurring cron shorthand. Also explain:

- Cron uses the runtime's local timezone and wall-clock slots. First wake is based on the next matching minute, not creation time plus a duration.
- Clock changes and DST affect elapsed spacing. A `1d` shorthand means local midnight slots, not a guaranteed 86,400-second interval.
- The scheduler adds a stable, nonnegative per-ID jitter before delivery. In current code, `*/N` minute expressions use `N` to compute the jitter bound; other minute fields use 30 as a fallback. For accepted recurring minute shorthand, jitter is below half that cadence; for accepted hourly/daily shorthand it is below 15 minutes. Nonrecurring cron jitter is below 90 seconds. Preserve these mechanics.
- Wakes may be delayed further while the agent is busy. This change does not provide an exact dispatch-time or elapsed-cadence guarantee.

### 5. Persistence and restoration

Do not add original-duration fields, conversion metadata, new result schemas, or journal versions. New creation stores the same normalized cron strings as before, now only after exact shorthand validation.

Previously saved daily or minute schedules remain valid. A stored `0 0 * * *` cannot reveal whether its original input was `1d` or `2d`. Never guess, rewrite, quarantine, or delete it as part of A05. Restoration and pause/resume continue using the stored cron, without reinterpreting it as shorthand.

Document this limitation in the release/README note: existing controllers retain their saved schedule; users who relied on shorthand should inspect `LoopList` and explicitly cancel/recreate an incorrect schedule. Do not automatically create replacements.

Test snapshot round-tripping through `LoopStore.snapshot()` / `restoreSnapshot()`, including a legacy normalized daily controller, a valid explicit non-table cron, an event controller, and a dynamic controller. A rejected new input must leave the snapshot and `nextId` unchanged and must not call `onChange`.

## Risks and review questions

| Question or risk | Recommended resolution |
| --- | --- |
| Is rejecting formerly accepted shorthand too disruptive? | Accept this deliberate safety change. Preserve all exact current table mappings, explicit cron, and saved schedules. Publish the accepted set and rejection examples. Silent frequency changes are worse than actionable errors. |
| Why not add exact `3m` or general interval timers now? | Keep the patch bounded. New accepted schedules need a separate contract and tests. `*/3 * * * *` is already available to users who explicitly want that wall-clock cron. |
| Why not retain rounding with warnings? | Reject instead. A warning still schedules a different frequency before the caller approves it, and creates metadata/restoration requirements. No approximation opt-in in A05. |
| Could new duration recognition steal an event name or goal? | Reserve only an entire duration-like tool input or command prefix followed by whitespace/end. Preserve explicit event intent and document it as the escape. Test `audit:1m`, `1month`, and goals with duration text later in the sentence. |
| Does "exact" imply exact elapsed wake spacing? | No. Use "exact table mapping" in technical text and the timing note in user output. Preserve and document current local-time and jitter behavior. |
| Should previously rounded saved loops be repaired? | No. Original intent is absent. Preserve saved cron and ask users to inspect/cancel/recreate intentionally. |
| Does rejecting invalid inputs need a new transaction layer? | No. These failures are decided synchronously before creation. Leave general scheduler-registration rollback and invalid restoration to A03. |
| Is the current hourly/daily jitter bound desirable? | It is existing behavior, not an A05 decision. Describe the actual minute-field fallback; do not silently change it or promise a cadence-derived bound. |

No actual blocker was found. The implementation review must explicitly acknowledge the input-acceptance change and narrow inference reservation rather than presenting this as a fully backward-compatible parser refactor.
