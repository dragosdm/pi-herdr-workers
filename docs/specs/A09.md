# A09: Atomic pause checkpoint persistence and restoration

## Status and objective

Specification only. No implementation is included. Source inspected at `3b2af2d`; the audit describes baseline `1643689`.

A successful `LoopUpdate` with `status: "paused"` must save the supplied checkpoint in the same authoritative snapshot as the pause. Reloading the controller and explicitly resuming it must expose that checkpoint to the next wake. An update-history entry alone does not satisfy this requirement.

## Problem and evidence

The tool accepts `state`, `metrics`, `doneCriteria`, and `prompt`, but its pause path discards them before updating the store. The controller pauses successfully with its previous checkpoint. After reload, work can resume with obsolete progress, measurements, completion criteria, or goal text.

## Scope and contracts

In scope:

- Ordinary dynamic-loop pause checkpoint updates through `LoopUpdate`.
- One authoritative snapshot containing both checkpoint and paused status.
- Restoration in session mode and explicit shared-file mode.
- Positive regression coverage of explicit resume and the next wake's checkpoint.
- Documentation of pause field semantics and the persistence boundary.

Non-goals:

- A08 wake identity, duplicate acknowledgement policy, iteration counting, or new administrative resume APIs.
- A11 expiry ordering, cron/hybrid parsing, monitor behavior, or worker readiness.
- Replaying old audit entries, inventing lost checkpoints, or repairing historical sessions automatically.
- Changing completion deletion into retained completed controllers.
- Changing generic `LoopDelete action="pause"`, slash-command pause, workflows, or orchestration settlement.
- Reworking file-store locking, Pi session durability, notification queues, or cross-process exactly-once execution.

Preserve these contracts:

- Same public tool names, parameters, enum values, result text, result tone, and loop ID.
- `completed` continues to delete the controller. Its supplied fields remain in the audit entry, not a retained completed checkpoint.
- The seven-day deadline, fire count, fire cap, controller cap, trigger, read-only flag, and recurring setting do not change.
- Pausing does not start a wake. Paused restoration does not re-arm the controller.
- Explicit shared files remain authoritative; session snapshots are their audit mirror. Memory scope remains ephemeral.
- Session matching and all-entry restoration remain as implemented. `/tree` does not rewind operational facts, and a new session does not inherit a session-scoped controller.
- Existing workflow and orchestration rejection paths remain intact.

## Recommended design

### Store API

Extend `LoopStore.stopDynamic` and the corresponding `LoopStoreLike` signature with a fourth, optional argument:

```ts
checkpoint?: {
  state?: string;
  metrics?: string;
  doneCriteria?: string;
  prompt?: string;
}
```

On the inspected baseline, keep the existing ID, status, expected-value argument order, and boolean result; existing three-argument callers remain valid. The recommended implementation base is the reviewed A08 change. Adapt this checkpoint argument to A08's updated `stopDynamic` signature rather than preserving an overload that bypasses mandatory wake identity. A09 itself adds no public tool field or stored-schema field. A small named checkpoint type is acceptable if it avoids repeating the field definition; do not introduce a general patch mechanism.

`stopDynamicLoop` passes those four fields from the tool parameters. It must not call a separate public `updateDynamic` before or after `stopDynamic`.

### Transaction behavior

For a pause, inside the existing single `withLock` callback:

1. Load and check the controller using the existing compare-and-set conditions. On the recommended A08 base, require and validate its current `wakeId` under this same lock. Complete all checks before any reducer event; rejected or previously consumed tokens cannot write a checkpoint.
2. Take one `at = Date.now()` value.
3. Apply `LOOP_DYNAMIC_UPDATED` with the checkpoint fields. Map a supplied `prompt` to both the top-level prompt and `dynamic.goal`. Set `dynamic.lastUpdatedAt` to `at`.
4. Apply `LOOP_PAUSED` with the same `at` and existing `kind: "administrative"` provenance. On the A08 base, consume the accepted wake token in this same transaction using A08's transition, not a second public store call.
5. Return true. Let `withLock` perform its single save and single `onChange` callback with the final snapshot.

The existing reducer already provides the required merge semantics. Prefer reusing its two events within one store transaction over a new reducer event or wider persistence refactor. `PERSIST_LOOP` effects are not storage commits in this store, and the current `onEffects` is a no-op. Tests must check externally saved snapshots, not confuse each reducer event with a persistence operation.

For completion, keep the existing deletion branch. Do not emit an intermediate checkpoint snapshot or apply a pointless update before deletion.

Field decisions:

| Input/field | Required pause behavior |
| --- | --- |
| Supplied `state`, `metrics`, `doneCriteria` | Replace that field exactly. No trimming or truncation. |
| Omitted checkpoint field | Preserve its current value. |
| Empty string | Save an empty string, allowing explicit clearing. It is not treated as omission. |
| Supplied `prompt` | Save both `entry.prompt` and `dynamic.goal`, including an empty string. |
| Omitted `prompt` | Preserve both existing prompt and goal, even if they differ. |
| `lastUpdatedAt`, `updatedAt`, `pause.at` | Use the single transaction timestamp. |
| `iteration`, `awaitingUpdate`, `nextWakeAt` | Preserve current values in the A09-only change. Existing pause semantics do not alter these fields. A08 owns any acknowledgement-related change. |
| `nextInterval` on pause | Continue to ignore it. It does not schedule or validate a new wake, including when malformed. Document that it applies only to continue. |
| All other controller fields | Preserve unchanged. |

Keeping scheduling fields unchanged is deliberate scope control. The paused status blocks scheduler execution. Current explicit `LoopStore.resume` clears `awaitingUpdate` when necessary; current continue replaces the wake schedule. A09 must not silently change either path. If implemented on an A08 base, preserve A08's acknowledgement and scheduling decisions while applying the checkpoint in the same transaction as its accepted pause.

An accepted pause with no checkpoint fields still pauses and records its dynamic update timestamp. It does not increment iteration or fire count. Do not add a new A09 rule about whether a second pause is permitted; retain the current admission policy or the reviewed A08 policy on a stacked base.

### Persistence, restoration, and migration

No stored-schema version bump is needed. `LoopEntry.dynamic` already has every required field. Keep `herdr-loops.snapshot.v1`, `herdr-loops.update.v1`, and the file snapshot format unchanged.

The restored source of truth remains the latest surviving session snapshot for the current session or the shared file. Do not replay update audit records during restoration. They do not prove which mutation committed, and replay could overwrite a newer checkpoint or revive deleted work.

Old snapshots restore unchanged. Existing lost pause data cannot be recovered reliably by this fix. A user may inspect history and deliberately submit a new authorized update, but migration must not do so automatically. Legacy session-file import must preserve whatever checkpoint actually exists in that file.

Atomicity means readers and persistence callbacks see either the previous controller or the paused controller with its entire accepted checkpoint, never a separately persisted active checkpoint or paused stale checkpoint. In session mode this is one snapshot append, not a disk fsync guarantee. The separate update audit entry remains supplementary. In shared mode use the existing locked snapshot writer and `.prev` recovery behavior; do not promise transactions spanning the shared file and Pi's audit log.

### Failure, cancellation, and concurrency

- Missing ID, wrong controller kind, or failed expected-value check must not mutate any checkpoint field, remove triggers, or append a successful update audit entry. Keep existing error results.
- A store persistence error must propagate without a success result. For memory-backed session mode, the existing `withLock` rollback must restore both checkpoint and status, and trigger removal must not have happened yet.
- After the authoritative snapshot commits, remove triggers as today, then append `herdr-loops.update.v1`. If this supplementary append fails, do not roll back a committed controller or reconstruct state from the audit. The tool may fail, and inspection must show the whole saved pause, never a partial checkpoint. Test this distinct boundary.
- Shared-file save or mirror failures retain the existing failure contract. A failure after rename can leave the full new snapshot committed even if the tool throws. Document uncertainty instead of asserting rollback or automatic retry. Do not change shared persistence internals for A09.
- The mutation is synchronous and has no `await` between validation and save. Keep this property. Do not add an asynchronous checkpoint write or detached task. Tool cancellation cannot split this transaction; there is no new abort protocol. Existing shutdown/persistence errors still surface.
- Use the existing expected status, iteration, and timestamp inside the file lock. If another writer has changed one of these before lock acquisition, reject the whole patch. A09 does not fix same-millisecond stale submissions or duplicate-wake admission; those belong to A08.
- Restoring a paused controller must not emit a wake. After authorized resume, a future wake must use the new checkpoint. Already queued notification payloads are historical wake records and are not retroactively rewritten by this change.

### Alternatives rejected

- Separate `store.updateDynamic` and `store.pause` calls produce two persistence points and a crash window. Reject.
- Mutating fields in the tool or in `get()` results bypasses store locking and reducer rules. Reject.
- Recovering checkpoint fields by replaying `herdr-loops.update.v1` gives a supplementary record authority it does not have. Reject.
- Adding a new snapshot schema or generic transaction framework is unnecessary for existing fields. Reject.
- Changing iteration or wake-token semantics here couples this small data-loss fix to A08. Keep that design in A08.

## Test matrix

Use distinct old/new marker values for every checkpoint field so accidental field swaps cannot pass. Use a fixed timestamp that differs from creation time. Capture immutable snapshots rather than references to live objects.

| Case | Required assertions |
| --- | --- |
| All checkpoint fields supplied | Paused controller contains every new value; prompt and goal agree; one final snapshot; administrative pause; same transaction timestamps. |
| Each field supplied alone | Only that field changes, apart from pause metadata and timestamps. Prompt-only updates both prompt and goal. |
| No checkpoint supplied | Existing checkpoint and goal survive. No accidental `undefined` replacement. |
| Empty strings, Unicode, multiline text | Values round-trip exactly. Empty string clears a value; rendering need not show an empty line. |
| Invalid field types | Registered schema rejects null, numeric, or object checkpoint values and invalid status values. Keep optional string fields unchanged; direct adapter calls are not schema-validation tests. |
| `nextInterval` supplied on pause | Valid and invalid intervals do not create a timer or replace `nextWakeAt`. |
| Scheduling invariants | Iteration, awaiting-update flag, saved next-wake time, fire count, cap, expiry, and read-only setting remain unchanged on the A09-only base. |
| One save boundary | `onChange` observes exactly one changed snapshot containing paused status and all new checkpoint fields. Never observe an intermediate active/new or paused/old snapshot. |
| Snapshot append throws | Memory state equals the old snapshot; no trigger removal; no successful audit append or result. |
| Supplementary audit append throws | Authoritative snapshot has the full pause; triggers were removed; no rollback to old fields. Recreate store from that snapshot successfully. |
| Session restoration | Fresh runtime reads saved snapshot without the update audit entry and restores all fields. A conflicting update audit record cannot override the snapshot. |
| File restoration | Use an absolute path under `mkdtemp`; reopen a second `LoopStore` and compare all fields. No writes under the real `~/.pi/loops`. Remove temporary directory in `finally`. |
| Shared-store conflict | Writer B changes the loop after A captured expected values; A's stale pause fails; reopening file shows B's whole state, no A fields. Use controlled distinct timestamps. |
| Snapshot compatibility | Old snapshots without optional metrics/done criteria remain loadable; no fabricated checkpoint from history. Memory scope does not gain persistence. |
| Restore while paused | Scheduler start/pump produces no wake. No pane creation or command launch. |
| Resume and next wake | Explicitly resume below cap and before expiry, dispatch one wake through runtime, and inspect its emitted dynamic data and rendered message for the new checkpoint. No old markers appear. |
| Limits after pause | Pause at the final allowed fire can save the checkpoint. Resume still fails at the cap or deadline; no renewed lifetime or cap. |
| Rejected target/update | Missing, non-dynamic, workflow-owned, orchestration-owned, stale expected status/iteration/timestamp: no checkpoint mutation or accepted-update audit. |
| Existing completion/continue | Completion still deletes. Continue still preserves omitted fields and follows existing validation. Generic administrative pause does not acquire checkpoint-writing behavior. |
| Shutdown/cancel boundary | Inject snapshot callback rejection to represent a closed runtime; no partial pause. No asynchronous commit exists to finish after cancellation. |

## Risks and review questions

| Question or risk | Recommended resolution |
| --- | --- |
| Are two reducer events atomic enough? | Yes for the current store: one lock, one final save, one `onChange`, no externally published reducer effects. Require an assertion at that actual persistence boundary. If future `onEffects` publishes intermediate states, revisit the event design then. |
| Should pause increment iteration or consume a wake token? | Preserve the baseline for A09. A08 owns that decision; checkpoint persistence must be part of its accepted transaction. |
| Should pause save prompt changes? | Yes. The public optional prompt field is a goal update, and silently discarding it recreates the same defect. Save prompt and goal together. |
| Should old update audits repair old checkpoints? | No automatic repair. Their ordering and acceptance are insufficient to make them authoritative. Document the limitation. |
| Does a returned pause prove power-loss durability? | No. It proves successful existing store persistence/append behavior, subject to Pi session storage. Keep README caveats and test the append-failure boundary. |
| Can already queued wakes be rewritten? | No. They represent earlier dispatches. Test the next newly dispatched wake after explicit resume, not a retroactive notification rewrite. |
| Will persistence failure require changing the base store? | Not for A09. Exercise memory rollback and shared-file reopening without promising stronger shared-file failure semantics. Report any independently reproduced generic persistence defect separately. |

No design blocker was found. The fix can be implemented independently on the inspected baseline, but the recommended stacked implementation should wait for A08's reviewed store interface to avoid conflicting token-admission changes.

## Definition of done

- [ ] A successful accepted pause stores supplied checkpoint fields and paused status in one authoritative snapshot.
- [ ] Omitted values preserve prior fields; empty strings clear fields; supplied prompt updates both prompt and goal.
- [ ] One transaction timestamp covers checkpoint and pause metadata, with no unrelated counter, limit, or lifetime changes.
- [ ] Snapshot failure, supplementary audit failure, and stale expected-value cases have distinct tested outcomes and no partial checkpoint.
- [ ] Session restoration works without the update audit; shared-file reopening preserves the checkpoint; historical audits do not override snapshots.
- [ ] Paused restoration does not fire. An authorized next wake after resume contains the latest checkpoint.
- [ ] Dedicated positive regressions pass, and the exact A09 `Known audit gap` test has become a positive regression without deleting unrelated coverage.
- [ ] `npm run typecheck`, full `npm test`, and `git diff --check` pass in the implementation worktree. Record command output and commit SHA in PR evidence.
- [ ] README documents field merge semantics, continue-only interval behavior, recovery limitations, and existing durability boundaries.
- [ ] Reviewer confirms the diff contains only A09 changes and coordinated conflict resolutions. Any A08 base is explicit and its acknowledgement rules are preserved.
- [ ] Implementation is committed and submitted in an authorized PR with the targeted reproduction-before/fix-after evidence, test results, and any live verification accurately labeled.
- [ ] Review does not treat passing defect reproductions as success or claim that these checks exclude every possible regression.
