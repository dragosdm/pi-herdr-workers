# A11: Awaiting-update loops must still expire

## Status and outcome

Specification only. This document does not implement the fix.

An active dynamic controller waiting for `LoopUpdate` must retire on the first eligible scheduler pump at or after its existing `expiresAt`. Waiting for the model blocks another work wake, not lifetime enforcement. Use the existing expiry transition, persistence, and notification path. Do not renew the controller or synthesize an update.

### Confirmed cause

`loop/scheduler.ts`, `CronScheduler.pump`, lines 120–176, scans two maps. The `expiryTimes` scan already expires due entries without an awaiting-update check. In the `fireTimes` scan, the checks currently run in this order:

1. Skip a timer that is not due.
2. Discard inactive or specially managed entries.
3. Skip dynamic entries awaiting an update.
4. Apply the execution filter.
5. Check `now >= entry.expiresAt` and call `retireExpired`.

Step 3 makes step 5 unreachable for a waiting dynamic loop whose timer lives in `fireTimes`. Repeated pumps cannot repair it. The execution filter can also suppress the expiry branch; the corrected ordering must treat that filter as a work-dispatch filter, not permission to extend a lifetime.

### Impact and limits of the evidence

A continuously running session can retain an active waiting controller past its lifetime. It can remain visible in `LoopList` and consume one of the 25 controller slots. Runtime retirement and its notification are delayed indefinitely while the waiting flag remains set. Reload follows a different path and retires the entry.

This does not demonstrate repeated external work: the waiting check prevents another scheduler work dispatch. It demonstrates missing retirement. It also does not establish any worker-startup timing claim. A04 is a separate observed readiness loss with a source-supported race hypothesis, not a captured interprocess ordering trace and not a dependency of this fix.

## Scope and compatibility

### In scope

- Reorder lifetime enforcement in the due `fireTimes` branch of `CronScheduler.pump`.
- Verify both timer-map paths, exact deadline behavior, waiting-state preservation before expiry, retirement callbacks, persistence, and restart behavior.
- Convert the A11 characterization to a positive regression and add a dedicated regression file.
- Clarify the existing README lifetime/recovery contract.

### Non-goals

- No change to seven-day lifetime, wake caps, recurrence defaults, or the 25-controller cap.
- No new timeout for a single model response and no automatic retry of interrupted external work.
- No new `LoopUpdate` token, duplicate-update fence, resume API, or pause checkpoint behavior. Those belong to A08 and A09.
- No cron parsing, creation rollback, or recovery-quarantine fix. Those belong to A03 and A05–A07.
- No change to paused-controller lifetime policy, workflow/orchestration ownership, monitor waits, or specially managed entries excluded by the existing scheduler guard.
- No wall-clock timer redesign, global store sweep on every pump, or extra heartbeat.
- No change to notification delivery guarantees, pending-wake cancellation policy, filesystem durability, or worker/monitor behavior.

### Contracts that remain unchanged

Tool names, parameters, return schemas, saved snapshot versions, event payloads, controller IDs, and deadline timestamps do not change. A normal dynamic controller is deleted on expiry, not paused merely because it has dynamic state. Do not confuse `retire`, which handles the fire cap and pauses dynamic loops, with `retireExpired`.

Expiry stops future scheduler work. It does not abort a model turn, kill a process, undo external work, or retract a wake already handed to Pi. The existing expiry notification may itself inform the agent; tests must distinguish that notification from the scheduler's `onFire` work callback.

## Recommended design

### Required pump ordering

Make a small local change in `CronScheduler.pump`. Keep the initial due-time test and existing inactive/special-controller guard. Immediately after that guard, move the existing expiry block ahead of both the waiting check and the execution filter:

```ts
// Existing due-time and active/special-controller checks remain above.
if (now >= entry.expiresAt) {
  this.retireExpired(entry, now);
  continue;
}

if (entry.trigger.type === "dynamic" && entry.dynamic?.awaitingUpdate) continue;
if (filter && !filter(entry)) continue;

// Existing onFire and rearm logic follows unchanged.
```

Remove the old copy of the expiry block. Add a short comment explaining that lifetime enforcement precedes work eligibility. Do not duplicate store deletion or callback logic here.

The unconditional `continue` after the retirement attempt is required. If `canExpire` returns false, the controller must neither retire nor dispatch work. Its timer remains available for the next eligible pump. A temporarily closed context must not become permission to execute overdue work.

### Exact behavior

| Condition | Required result |
| --- | --- |
| Waiting and `now < expiresAt` | Leave controller and checkpoint unchanged; no work callback and no expiry callback. |
| Waiting and `now === expiresAt` or later | Run existing retirement path without consulting the work filter. Ordinary dynamic entry disappears, timer registration is removed, and one expiry callback reports `deleted`. No work callback. |
| Not waiting and overdue | Same existing retirement behavior, now also independent of a rejecting work filter. |
| Due but unexpired, filter rejects | Do not fire or retire. Filtering semantics before expiry are unchanged. |
| Computed wake at or after deadline | Existing `expiryTimes` behavior remains. Expire at the deadline, not at the later requested wake. |
| `canExpire` rejects retirement | No mutation, callback, or work. Retry on a later pump when allowed. |
| Repeated pump after successful retirement | No additional expiry callback, no new persistence transition, no work. |
| Loop paused or deleted before pump | Preserve existing inactive-entry handling; do not reactivate or label cancellation as successful expiry. |

`pump` receives an internal finite millisecond clock value. Keep its existing signature and input contract. This change does not add public validation for `NaN`, infinity, or malformed persisted deadlines. Boundary tests use valid numeric timestamps, not invented guarantees for corrupt state.

### API, storage, and restoration

No schema change or migration is needed. Reuse `LoopStore.expireEntry` so existing session snapshots, shared-file locks, callbacks, and deletion/pause rules remain authoritative.

On upgrade, an already registered overdue waiting loop retires on the next eligible pump. On reload, existing recovery expires overdue entries before trigger registration. A saved unexpired waiting entry remains waiting after restoration and cannot dispatch another work wake; it still expires when the deadline arrives. Do not clear `awaitingUpdate` or assign a new `nextWakeAt` to make expiry reachable.

Preserve the original `expiresAt`; no recovery grace period or automatic recreation. After ordinary dynamic expiry, `LoopUpdate` finds no controller and cannot recreate it. A `continue` attempted after the deadline but before the pump remains rejected by the existing tool/store checks. Tests of these checks must mock the wall clock as well as the scheduler clock.

### Errors, cancellation, and ordering

`retireExpired` owns the transition. Keep its existing ordering: store transition first, timer removal second, expiry callback last. If a memory-store persistence callback throws, the store rolls back, the pump propagates the error, and the timer remains eligible for retry. Test this bounded failure/retry case. Do not add a catch that reports expiry despite failure.

The production expiry callback already catches event-listener and notification errors. Do not add retries or exactly-once claims for external notification delivery. A callback error cannot authorize another work wake after the store has retired the entry.

The pump is synchronous. Model updates and expiry execute serially in one runtime. Test both meaningful orderings: update before deadline followed by expiry, and expiry followed by an attempted update. Shared-file stores still re-read under their existing lock; no new cross-process ownership guarantee is introduced. A store transition rejected because an entry was already removed must not emit another expiry callback.

Explicit deletion and pause remain valid cancellation/blocking actions. Shutdown still clears timer maps through `stop`; a stopped scheduler does not continue retirement work. Persisted expiry is reconciled through normal recovery on restart.

### Alternatives rejected

- Moving only the waiting check below expiry but leaving the filter above expiry leaves lifetime enforcement dependent on dispatch eligibility. Move expiry ahead of both.
- Clearing `awaitingUpdate` on a timer or reload risks repeating external work and violates the recovery contract.
- Calling `store.delete` directly bypasses pause dispositions, persistence semantics, and existing expiry notifications.
- A second expiry-only timer or a store-wide sweep adds unnecessary scheduling behavior and affects excluded controller types. The existing due maps already reach the affected entries.
- Automatically pausing all dynamic loops on expiry changes an established deletion contract and does not belong in this fix.

## Risks and review decisions

| Review question or risk | Recommended resolution |
| --- | --- |
| Should waiting dynamic expiry pause instead of delete to retain the checkpoint? | No. Use existing `expireEntry` policy. Retention changes would need a separate product decision and storage contract. |
| Does moving expiry before the filter broaden behavior? | Yes, intentionally and narrowly: a work-dispatch filter cannot extend a due active controller's lifetime. Preserve the filter's unexpired behavior and add explicit tests. |
| Should every paused or specially managed controller also expire in this pump? | No. Leave existing guards and ownership boundaries unchanged. This spec fixes registered active scheduler-managed entries. |
| Does a 30-second heartbeat mean expiry is always within 30 seconds? | No. Runtime suspension, busy event loops, or blocked context can delay pumping. Promise retirement on the first eligible pump, not a wall-clock service guarantee. |
| Could this repeat or cancel in-flight external work? | Do neither. The waiting flag is untouched before expiry; retirement prevents later dispatch but does not abort existing work. |
| Could a callback or persistence failure cause false success? | Reuse helper ordering. Test rollback/retry for memory persistence and one callback after success. Keep existing notification failure boundaries; do not claim crash-proof exactly-once delivery. |
| Could a shared-file race invalidate an in-memory entry? | Keep the locked store transition and current-entry recheck. Do not inline deletion or mutate the entry object. No new distributed ownership claim. |
| Is a passing original audit test enough? | No. It asserts the defect. The inverted regression must fail before the reorder and pass afterward. |

No actual blocker was found. Any later requirement to change retention policy, lifetime length, or update schemas is outside A11 and must not silently expand this implementation.

## Definition of done

- [ ] The due `fireTimes` branch checks expiry before waiting status and the execution filter, while preserving the existing active/special-controller guard and `canExpire` behavior.
- [ ] Ordinary awaiting dynamic loops retire at the exact deadline and after it without another work wake or model response.
- [ ] Unexpired waiting loops preserve their checkpoint and do not repeat work, including after snapshot restoration.

- [ ] Deferred permission and failed memory persistence do not dispatch overdue work or falsely acknowledge retirement; bounded retries are covered.
