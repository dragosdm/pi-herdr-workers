# A07: Accept complete cron expressions in hybrid triggers

## Status and decision

Specification only. This file does not implement the fix.

Keep the existing `LoopCreate` string API and stored `HybridTrigger` shape. Replace its one-token extraction with a small, fully consuming hybrid grammar. Pass the entire extracted schedule to the existing `parseInterval()` function. Document the grammar in the tool schema description and README. Do not add structured tool parameters or a storage migration.

## Problem and verified evidence

A hybrid loop combines a cron schedule with an event subscription. Today, a caller cannot use the documented kind of five-field schedule in the normal labeled hybrid form:

```json
{
  "trigger": "cron: */5 * * * * event: audit:test",
  "triggerType": "hybrid",
  "prompt": "Check the audit state",
  "maxFires": 1
}
```

`LoopCreate` extracts `*/5`, calls `parseInterval("*/5")`, and rejects creation. The caller cannot select a complete schedule while naming the event this way. The shorthand `cron: 1h event: audit:hybrid` works.

## Scope and non-goals

### In scope

1. Complete schedule extraction from hybrid strings.
2. A documented, unambiguous grammar with deliberate compatibility aliases.
3. Rejection of malformed hybrid strings without creating a loop or subscribing to an unintended source.
4. Positive tests through `LoopCreate`, scheduler/event registration, cancellation, and restoration of healthy hybrid controllers.
5. README and tool-description examples that callers can copy.

### Explicit non-goals

- Changing cron dialect, day-of-month/day-of-week matching, search horizon, timezone, DST, jitter, or elapsed-time semantics. A06 owns cron semantics.
- Fixing zero/long interval normalization or deciding how to report rounding. A05 owns that policy. Hybrid schedules must use the same `parseInterval()` behavior as ordinary cron schedules, including any later A05 correction.
- General transactional creation, scheduler-registration rollback, or quarantine of invalid restored entries. A03 owns those fixes. This parser must reject its own errors before persistence; it must not claim to solve failures after store creation.
- Changing hybrid debounce semantics, coalescing scheduler fires with event fires, or introducing exactly-once wake guarantees.
- Changing broad trigger-type inference, adding a hybrid slash-command route, new event filters, quoted event names, or structured tool arguments.
- Changing dynamic loops, monitor behavior, worker readiness, or any other audit finding.

### Contracts to preserve

- Keep required `trigger` and `prompt`, existing optional fields, `additionalProperties: false`, and all parameter types unchanged. Only descriptions need schema edits.
- Explicit `triggerType: "event"` remains authoritative even if its source contains `cron`, `event`, or `hybrid`.
- Canonical hybrid input with both labels continues to work when `triggerType` is omitted through existing inference. Bare or cron-only compatibility forms need explicit `triggerType: "hybrid"` to be hybrid.
- Keep current defaults: `recurring: true`, `debounceMs: 30000`, `maxFires: 25`, and existing read-only behavior. Explicit zero debounce remains zero; use `??`, not `||`.
- Keep the 25-controller cap, seven-day lifetime, fire caps, pause/delete behavior, output shape, IDs, journal scopes, and persisted trigger type unchanged.
- Keep existing structured hybrid records, including optional stored event filters, restorable without reparsing them as user input.

## Recommended design

### Public grammar

The preferred spelling is:

```text
cron: <schedule> event: <source>
```

`<schedule>` is either a full five-field cron expression or a shorthand accepted by `parseInterval()`. It must be passed whole to that function. `<source>` is exactly one nonempty whitespace-delimited token. Colons inside the source are ordinary characters, so `audit:test`, `monitor:done`, and `audit:event:done` must survive unchanged. Event source case is preserved.

Rules:

1. Trim outer whitespace. Accept one or more whitespace characters between schedule fields and clauses, including tabs and newlines. Normalize whitespace inside the extracted schedule to single spaces before `parseInterval()`; do not rewrite cron punctuation or event names.
2. Labels are the lowercase words `cron` and `event`. A label uses a colon with optional whitespace after it, or at least one whitespace character when the colon is omitted. Thus `cron:1h event:audit`, `cron: 1h event: audit`, and `cron 1h event audit` are accepted. `cron1h eventaudit` is not.
3. Preserve event-first order as a compatibility form: `event: audit cron: 1h` and `event: audit cron: */5 * * * *`. The preferred documented examples stay cron-first.
4. Preserve explicitly hybrid inputs containing only `cron: <schedule>` or bare `<schedule>`. They use `tool_execution_start`, matching current behavior. Document this compatibility default, but prefer an explicit source in examples.
5. A present but empty event clause is an error. It must never use the missing-clause default. An event-only input is also an error because a hybrid needs a schedule.
6. Consume the whole string. Reject leading junk, trailing junk, repeated clauses, extra event-name words, missing schedules, and incomplete schedules. Do not silently keep the first recognized field or ignore remaining words.
7. Do not support a `hybrid:` prefix, JSON in the trigger string, named cron macros, a sixth seconds field, or a year field. Quotes and backslashes have no special parsing meaning: they cannot escape whitespace, and single-token sources are not unquoted or unescaped. Cron syntax beyond extraction is whatever the shared cron parser supports. Do not duplicate its validator or add an independent dialect here.

Supported forms are therefore exactly:

```text
cron-label schedule event-label source
event-label source cron-label schedule
cron-label schedule
schedule
```

Outer indentation is insignificant. The last two forms are compatibility forms whose hybrid meaning requires explicit `triggerType`.

Examples and expected normalization:

| Input with hybrid type | Stored cron | Stored source |
| --- | --- | --- |
| `cron: */5 * * * * event: audit:test` | `*/5 * * * *` | `audit:test` |
| `cron: 0 9 * * 1-5 event: tool_execution_end` | `0 9 * * 1-5` | `tool_execution_end` |
| `cron: 0,30 9-17 * * 1-5 event: audit:event:done` | `0,30 9-17 * * 1-5` | `audit:event:done` |
| `cron: 1h event: audit:hybrid` | `0 * * * *` | `audit:hybrid` |
| `event audit cron 1h` | `0 * * * *` | `audit` |
| `1h` or `cron: 1h` | `0 * * * *` | `tool_execution_start` |
| `*/5 * * * *` | `*/5 * * * *` | `tool_execution_start` |

Previously tolerated arbitrary junk is not a compatibility contract. The new parser intentionally rejects strings the loose regexes partially consumed. State that tightening in the README rather than silently accepting them forever.

### Parser and integration

Add `loop/hybrid-parse.ts` with a pure exported helper:

```ts
parseHybridTriggerInput(input: string): {
  schedule: string;
  eventSource: string;
}
```

The helper extracts and normalizes the complete schedule and the source according to the grammar. It has no access to the store, scheduler, event bus, current time, or filesystem. Use fully anchored alternatives for the two labeled orders and the compatibility forms. Match whole labels, not substrings. A `cron:` or `event:` substring inside a source must not start another clause. Avoid independent unanchored `match()` calls.

The helper handles clause structure; `parseInterval()` remains responsible for validating the extracted schedule. A nonempty malformed schedule can therefore leave the helper but must fail before `store.create()` in `LoopCreate`. Do not let a failed two-clause parse turn into an accepted cron-only string with discarded text. A fallback must still consume and validate all remaining text as the schedule.

In `LoopCreate.execute()` replace only the hybrid extraction branch:

1. Extract `{ schedule, eventSource }` with the helper.
2. Call `parseInterval(schedule)` once. Retain its result in the tool so A05 can use its normalization metadata without changing this helper's contract.
3. Construct `{ type: "hybrid", cron: parsed.cron, event: { source: eventSource }, debounceMs: debounceMs ?? 30000 }`.
4. Continue through existing validation, store creation, trigger registration, result formatting, and lifecycle handling.

Do not change ordinary cron, event, or idle branches. Do not move persistence earlier. Do not add a second scheduler, schedule cache, or timer.

### Errors and cancellation

- Clause parsing errors must throw an `Error` whose message starts with `Invalid hybrid trigger:` and names the missing/invalid part. Include the preferred example `cron: */5 * * * * event: audit:test`.
- If `parseInterval()` throws in the hybrid branch, wrap that failure with the same hybrid prefix, preserve its useful original message, and include the example. Ordinary cron error messages remain unchanged.
- All these parsing/validation failures occur before `store.create()`, `TriggerSystem.add()`, `appendEntry()`, or widget updates. Assert no snapshot mutation, no consumed ID, no subscription, and no scheduled next fire.
- Do not broadly catch errors from persistence or trigger registration and turn them into apparent success. A03 owns their transaction policy; preserve that implementation if A03 lands first.
- Parsing is synchronous and introduces no new cancellation point or resource. Do not add an abort-signal API. Existing `LoopDelete` pause/delete, trigger removal, and shutdown must continue to remove both scheduling and event/debounce resources. A07 tests cancellation after a hybrid is created and while an event debounce is pending.

### Persistence and restoration

No schema version changes, new journal entries, or migration are needed. A normalized full cron already fits `HybridTrigger.cron`. The raw input string is not the stored contract.

- Old shorthand-created records restore exactly as before.
- New full-cron records restore through the same snapshot path and register both timer and event source.
- Restoring does not call the new parser, invent an event source, create another controller, or dispatch an immediate catch-up wake.
- Stop the old trigger system before constructing/restarting the restored runtime in tests. Runtime subscriptions and timers are not serialized.
- A full-cron A07 parse failure currently creates no record, so there is nothing to migrate for that failed request. Invalid schedules already persisted through other paths remain A03's recovery responsibility.

### Alternatives rejected

- Adding `cron` and `event` tool parameters would create two parallel input representations and precedence rules. The existing string and persisted structure can handle the fix without an API transition.
- Expanding `\S+` to an unrestricted greedy capture without an anchored grammar still accepts ambiguous junk and can capture the event clause as cron text.
- Writing a new cron parser here would diverge from A05/A06 and ordinary cron tools.
- Requiring both labels with colons in cron-first order only is simpler, but unnecessarily breaks currently usable compatibility forms. Preserve the bounded forms listed above instead.
