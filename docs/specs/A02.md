# A02: Read monitor tails as terminal text

## Status and purpose

This is an implementation specification, not a fix. It covers only audit finding A02. The target is readable, bounded `MonitorList` output on Herdr 0.8.0 without changing how monitors launch, attach, stop, or restore.

## Problem and verified evidence

`HerdrMonitorManager.readTail()` passes `herdr pane read` through a helper that expects JSON. Terminal text is not a JSON response. Ordinary logs therefore fail to parse, while empty stdout becomes a fabricated `{}` tail. Users cannot inspect readiness markers, errors, or final output through `MonitorList` even when the pane contains them.

Source references below use the specification checkout's pre-fix line numbers. Function names are the stable references if another finding changes nearby lines.

## Scope and contracts

### In scope

- A separate raw stdout path for text-producing Herdr commands.
- Text extraction, empty-capture handling, terminal-control cleanup, and tail boundaries.
- `MonitorList` presentation and cancellation for its read path.
- Positive regression tests through both the real manager with injected `exec` and the registered tool.
- User documentation and a bounded live compatibility check on Herdr 0.8.0.

### Non-goals

- A01 readiness/launch changes, tab-name matching, command identity, process exit codes, or stronger ownership checks.
- Changes to any loop scheduling, worker mailbox, lifecycle, or other audit finding.
- Reading full scrollback, streaming logs, caching tails, storing output in session entries, or building a new terminal emulator.
- Fixing Herdr itself or automatically falling back between different snapshot sources.
- New packages, shell pipelines, version probes on every list call, or CLI/API auto-detection.

### Compatibility to retain

- Keep `MonitorCreate`, `MonitorList`, and `MonitorStop` names and parameter schemas unchanged. `MonitorList` still takes `{}`.
- Keep `readTail(paneId, lines = 5, signal?) -> Promise<string[]>`.
- Metadata and mutation commands still use JSON interpretation, including the existing successful-empty-stdout `{}` behavior for those commands. Do not globally make JSON errors fall back to text.
- Keep the 15,000 ms timeout, required Herdr environment, argument-array execution, nonzero/killed rejection, and cancellation checks before and after execution.
- Keep `recent-unwrapped` as the source, the tool's five-row maximum, and 100-code-unit limit per output row. Keep roster order, status/age/header formatting, summary counts, `displayRows()` behavior, and `textResult()` shape.
- Status remains an observation of the foreground process. A tail is terminal context and can include a prompt or previous run's output. It is not proof that the requested command launched, completed, or succeeded.
- Preserve command keys, monitor IDs, serialization of create/stop, ownership guards, cap, retained panes, and all snapshot/session-scope behavior.

## Recommended design

### 1. Separate execution from JSON interpretation

In `HerdrMonitorManager`, introduce a private `herdrText(args, signal?) -> Promise<string>`. Move the existing environment check, signal composition, execution, post-execution abort check, and exit/killed checks into it. Return `result.stdout` exactly as captured on success. Do not trim it, parse it, substitute stderr, or fabricate an object.

Keep the existing private `herdr()` name for A01 and other call sites. Implement it as a thin wrapper around `herdrText()` that retains the existing `stdout.trim() ? JSON.parse(stdout) : {}` behavior. No existing metadata/mutation caller should switch to the text path.

Do not add `--raw`: its semantics are not needed for this change. The verified command already captures text through stdout. Explicitly request `--format text` rather than relying on a default.

### 2. Define `readTail()` precisely

Validate `lines` before any CLI invocation. It must be a positive safe integer. Reject zero, negatives, fractions, `NaN`, and infinities with a `RangeError` explaining the requirement. This is an internal method boundary; there is no new tool parameter or user-configurable count. The only production caller continues to pass five. Do not silently coerce or round.

Execute exactly one read:

```text
herdr pane read PANE_ID --source recent-unwrapped --lines LINES --format text
```

Use `herdrText()`, not `herdr()`. Treat stdout as text even if it happens to be `{}`, `null`, a JSON string, or an object-shaped log message. Never unwrap a `result.text` or `result.output` property from pane text.

Normalize the captured stdout in this order:

1. Remove ANSI/VT escape sequences using Node's built-in `stripVTControlCharacters` from `node:util`. This includes common color codes and OSC hyperlink wrappers. No runtime dependency is needed.
2. Normalize CRLF and remaining carriage returns to LF. A lone carriage return is a line boundary, not an invitation to implement terminal cursor movement.
3. Replace remaining C0/C1 control characters, except LF, with a single space each. This includes tabs, NUL, BEL, DEL, and residual ESC bytes. Printable Unicode is retained. This is safe log presentation, not a complete emulation of all possible terminal controls.
4. Split on LF. Drop rows whose `trim()` is empty. Preserve leading/trailing spaces on retained rows.
5. Return the last `lines` retained rows. Do not truncate individual rows in the manager; the tool's existing 100-code-unit display limit remains the presentation boundary.

A zero-length, whitespace-only, or controls-only successful capture returns `[]`. It must never return `["{}"]` unless the terminal actually printed `{}`. There is no retry and no fallback to another snapshot source. One read is a point-in-time observation; the CLI can return fewer rows than requested.

### 3. Distinguish empty capture from read failure

In `MonitorList.execute()`:

- Nonempty tail: keep the existing prefix and per-row truncation, using the normalized strings.
- Empty tail: append exactly `  | (no output captured)`.
- Non-cancellation read error: keep exactly `  | (could not read pane)` and continue to the next monitor.

The empty marker deliberately says nothing about whether the command ran or whether the pane contains older output. It means this successful request captured no displayable text. Stderr from a successful CLI call is diagnostic noise, not terminal output; do not show it as a tail. On failure, do not expose partial stdout as successful output.

Do not change status because a read failed. `refresh()` continues to own status updates. The list response remains informational and can include successful tails alongside a failure marker for another pane.

### 4. Cancellation and lifetime

Retain the combined caller/lifetime signal passed to `exec`. An already-aborted signal must prevent execution. Abort after `exec` resolves must still prevent publication of the result. Killed executions without an aborted signal remain ordinary read errors.

The current tool catch checks only the caller signal, so manager disposal can otherwise become an ordinary failure marker. Add a small manager method `throwIfAborted(signal?: AbortSignal): void` that checks the caller signal and then the manager lifetime signal. Use it in `herdrText()` around execution and in `MonitorList` at entry, in the tail catch, and immediately before widget/result publication. Preserve the composed signal for aborting the actual subprocess. This internal TypeScript method is not a tool API or persisted field.

Caller cancellation and `dispose()` must reject the pending list rather than return a successful placeholder or partial list. Do not create new reads for later monitors after cancellation. A read is observational, so cancellation performs no rollback, sends no keys, closes no pane, and leaves no cache. Do not broaden this work into a cancellation redesign for create, stop, or loops.

### 5. Persistence, restoration, and concurrency

There are no persistence/schema migrations. Do not change `HerdrMonitor`, `MonitorSnapshot`, `herdr-monitors.snapshot.v1`, or its scope. Existing snapshots restore exactly as before, with `unknown` status followed by refresh. The first post-restore list performs a fresh text read; it does not replay or restore tails.

Reads do not join the mutation queue or mutate monitor metadata. Two overlapping reads can complete in either order and must return their own captured text. A pane disappearing between refresh and read produces a read-failure marker for that row; a later successful read must recover without resetting the manager. There is no cross-pane cache to contaminate subsequent requests.

### Alternatives rejected

- A direct socket snapshot API adds an unverified protocol dependency when the installed CLI already provides text stdout.
- Trying JSON first and falling back to text corrupts JSON-looking application logs and hides metadata protocol failures.
- Serializing unknown values into a tail repeats the fabricated-output bug.
- Treating empty stdout as an exception conflates an empty successful snapshot with a transport failure.
- Switching to ANSI output or replaying cursor controls makes a short log tail a terminal-emulation feature.
- Parallelizing all list reads is unrelated to parsing and introduces ordering/cancellation changes. Keep sequential listing.

## Test matrix

| Case | Required assertion |
| --- | --- |
| Ordinary CLI text | `AUDIT_SERVER_READY\n` resolves to one row, without JSON parsing. Verify exact argv, command `herdr`, timeout, and signal. |
| Text without final LF | Returns its final line unchanged. |
| JSON-looking logs | `{}`, `null`, quoted text, and `{"result":{"text":"not an envelope"}}` remain literal rows. |
| Empty variants | `""`, newlines, spaces/tabs, and ANSI-only input return `[]`; tool shows exactly one empty-capture marker, never fabricated `{}`. |
| Line boundaries | CRLF and lone CR normalize; blank rows do not consume returned-row slots; retained indentation stays intact. |
| Count boundaries | Default five, explicit one, exactly N, fewer than N, more than N; output is the last N nonblank rows. Invalid counts reject before exec. |
| ANSI/control/Unicode | Color resets and OSC-8 wrappers disappear; remaining unsafe control bytes cannot reach the list; Unicode text survives. Include BEL, NUL, tabs, and DEL. |
| Long output | A fixture with at least 100 rows and a 10,000-character last row returns only the last five; list emits at most five tail rows, each at most 100 code units after the prefix. Check content and expanded details. |
| Successful stderr | Nonempty stderr does not replace or supplement stdout. |
| Read failures | Nonzero exit, killed result, and rejected exec cause manager rejection. Tool emits failure marker and still reads the next monitor. Partial stdout is not shown as a tail. |
| Environment guard | Missing/incorrect `HERDR_ENV` or missing workspace rejects before exec. |
| Caller abort | Before execution and while deferred exec is pending: rejection, no successful tool result, no later-pane read. Check the signal given to exec becomes aborted. |
| Disposal | Pending read/list rejects after `dispose()` even without a caller signal. A late successful exec resolution cannot produce a successful list or widget publication. |
| Concurrent reads | Two pane reads resolve in reverse order with separate expected text. No shared output state or persistence callback. |
| Recovery | One failed read followed by success works; pane vanishes between refresh/read without losing other rows. |
| Restore | Existing snapshot keeps IDs/key/cwd/command, starts `unknown`, and refresh/list reads current text. No launch/send-keys/tab-create operation and no persisted tail. |
| Metadata no-regression | JSON `pane get`/`process-info` still drive refresh correctly; malformed nonempty metadata JSON still fails inside the JSON helper and causes `refresh()` to report `error`; empty successful metadata/mutation output retains `{}` semantics. ## Risks and review decisions

| Question or risk | Recommended resolution |

| Is raw text output actually supported by the installed CLI? | Yes, verified with Herdr 0.8.0 help and a successful read of this worker's own pane. Retain a disposable marker capture in implementation evidence. Do not claim support for untested CLI versions. |
