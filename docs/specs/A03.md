# A03: Failed cron creation must not poison loop recovery

## Status and intended outcome

This is an implementation specification, not a fix. The specification was checked against the current source in this checkout and the 20 September 2026 audit. No production files were changed while writing it.

A failed scheduled-loop creation must leave no controller behind. When an older snapshot already contains an unschedulable controller, recovery must pause that controller with an inspectable reason and continue restoring healthy loops. A healthy event must actually fire after recovery; merely avoiding a startup exception is insufficient.

## Problem and evidence

`LoopCreate` parses `0 0 31 2 *` as a syntactically valid five-field cron. It then persists an active entry before asking the scheduler for its first occurrence. Finding an occurrence throws. The tool reports an error but the saved entry survives.

On reload, the scheduler visits that entry and throws again. `TriggerSystem.start()` calls the scheduler before subscribing to events, so it never installs the healthy event subscriptions. This affects unrelated controllers in the same store and contradicts the README's reload/resume contract.

## Scope and compatibility

### In scope

1. Reject unschedulable cron and hybrid timer schedules before creation persists them.
2. Remove a new controller and any partial registration if registration still fails after creation.
3. Recover old unschedulable entries independently, retaining them paused for inspection instead of blocking healthy subscriptions.
4. Prevent a manual resume from reactivating the same unschedulable entry.
5. Expose the recovery reason through loop inspection and document remediation.
6. Test session snapshot and file-store recovery, not only an in-memory scheduler.

### Non-goals

- Change cron day matching, search horizon, timezone, daylight-saving behavior, jitter, interval rounding, or hybrid grammar. A05, A06, and A07 own those decisions.
- Fix runtime expiry of an awaiting dynamic update, dynamic update fencing, or pause checkpoints. Those are A11, A08, and A09.
- Rewrite all store corruption recovery, persistence durability, shared-store ownership, or transactional behavior across multiple processes.
- Turn the scheduler into a timer service or add a cron dependency.
- Fix arbitrary event-provider subscription failures during startup, runtime re-arm failures after successful startup, workflow admission, monitors, or worker readiness.
- Delete historical audit records or rewrite old session JSONL entries.

### Contracts to preserve

Keep `LoopCreate`'s input schema, defaults, successful result format, event inference, recurring flag, `readOnly`, and `maxFires` behavior. Preserve the 25-controller cap and seven-day lifetime. Scheduled/event slash loops still default to 25 wakes; dynamic slash loops still default to 20.

Keep the current cron resolver as the authority for whether an occurrence can be found. An occurrence beyond `expiresAt` is not a scheduling error: the existing scheduler arms expiry instead of a fire. Do not equate "no fire during this controller's lifetime" with an invalid schedule.

Preserve event filters, hybrid debounce, ordinary pause/delete behavior, dynamic wake delivery and awaiting-update state, workflow/orchestration skip rules, and read-only gating. Recovery must not emit a wake for a quarantined entry or replay a delivered wake.

Keep the current persistence scopes: memory is ephemeral; session scope uses `herdr-loops.snapshot.v1`; explicit shared/project scopes use locked files and the session-log mirror. The session journal's visibility is not proof of power-loss durability.

## Recommended design

### 1. Validate before allocating and persisting

Add a small internal schedule-preflight helper in `loop/store.ts`, using the existing `cronToNextFire()` from `loop/loop-parse.ts`:

- A cron trigger resolves `trigger.schedule`.
- A hybrid trigger resolves `trigger.cron`.
- Event and plain dynamic triggers do not run cron resolution.
- The helper must not mutate an entry, allocate an ID, emit a notification, subscribe to events, or append a snapshot.

Call it inside `LoopStore.create()`'s existing lock, after the existing admission checks and before `LOOP_CREATED`. Use the captured creation time as the resolver's reference date. A resolver failure propagates as an error. For syntactic and scheduling failures, the store snapshot, `nextId`, and persistence callbacks must be unchanged. This covers both tool and slash-command creation without duplicating their parsing logic.

Do not validate all restored entries during deserialization. Old poison must load successfully so startup can pause it independently; rejecting the whole snapshot would recreate the cross-controller failure in a different layer.

Call the same preflight in `LoopStore.resume()` before `LOOP_RESUMED` and before clearing pause provenance. Keep existing expiry, terminal, and fire-cap checks. A failed preflight leaves the paused entry byte-for-byte unchanged.

Do not add new restrictions based on the seven-day lifetime. Preflight asks whether the existing resolver succeeds, not whether the schedule fires before expiry. A06 may later improve what the resolver accepts without changing this contract. Until A06 lands, a valid leap-day schedule beyond the resolver's horizon still fails safely; describe it as unavailable to this scheduler, not mathematically impossible.

### 2. Roll back registration failures without hiding them

In `LoopCreate.execute()`, capture the store and trigger system used for this creation. After `create()` succeeds, wrap only trigger registration in a guarded block:

1. Call `triggerSystem.add(entry)`.
2. If it throws, attempt `triggerSystem.remove(entry.id)` and `store.delete(entry.id)`. Attempt both cleanups even if the first fails.
3. Refresh the widget after cleanup, without allowing a widget error to replace the primary registration error.
4. Reject the tool call with the original registration error when cleanup succeeds. If cleanup fails, report the original error plus cleanup failures and the controller ID. Never report creation success or claim rollback succeeded when it did not.

A late failure may consume an ID and append creation/deletion snapshots. IDs remain monotonic; do not decrement `nextId`, restore a whole-store snapshot, or erase another writer's changes. The stronger zero-mutation guarantee applies to schedule preflight failures.

The rollback boundary ends when registration succeeds. Leave `onDynamicLoopActivated` after that boundary. Do not delete a valid dynamic controller merely because a later activation callback or rendering step fails after work was dispatched. This fix is not an external-side-effect transaction.

Make `TriggerSystem.add()` clean up that entry's scheduler state and any owned subscription if adding its event half throws. This protects the hybrid case where timer registration succeeds before event subscription fails. Keep the original error visible to its caller. The tool-level cleanup is still necessary to delete the new store entry and is safe to call again.

Retain the slash command's creation rollback. Adjust its cleanup only as needed to attempt both cleanup operations and preserve the primary error. On manual resume, catch preflight errors and show an error notification without a success notice. If registration fails after a successful resume, remove partial registration and return the entry to an administrative pause with a bounded registration-failure reason. Do not delete an existing controller merely because resume failed.

Creation and registration remain synchronous; do not introduce an `await` between store mutation and trigger registration. If the tool receives an already-aborted signal, reject before creation. An abort arriving after the synchronous commit is not permission to silently delete the controller. No retry timers or queued cleanup workers are needed.

### 3. Quarantine a bad restored schedule and keep restoring

Use the existing paused status and pause schema. Do not add a `quarantined` status, a new pause kind, or a new snapshot version.

In `CronScheduler.start()`:

1. Clear its scheduling maps before rebuilding them so repeated startup does not retain stale registrations.
2. Keep current skip rules for inactive, orchestration-owned, waiting-monitor, and terminal-workflow entries.
3. Resolve and arm each eligible entry independently.
4. If next-occurrence resolution fails, remove that ID's fire and expiry timers, then persist `store.pause(id, "administrative", reason)`.
5. Use a reason beginning `Schedule unavailable: ` followed by the resolver's error text. Let `LoopStore.pause()` trim/bound it to 512 characters. Preserve the original trigger, prompt, counters, ID, and expiry.
6. Continue to the next entry after that pause succeeds.

Keep the catch boundary narrow. Add an internal `ScheduleResolutionError` in `loop/scheduler.ts` that wraps failures from `computeNextFire()` only, with the original message and cause. Catch that class during startup. Do not swallow failures from `store.list()`, `store.pause()`, persistence, or arbitrary scheduler code as if they meant an invalid cron.

If writing the pause fails, leave the bad ID unarmed and propagate an explicit persistence error. Durable recovery cannot be promised while storage itself rejects mutations. A03's healthy-controller recovery guarantee assumes the existing store can load and write. This is a real infrastructure boundary, not a reason to return false success.

`TriggerSystem.start()` should stop its existing registrations before rebuilding, then call `scheduler.start()`, then obtain a fresh `store.list()`. Its existing active-status check will skip newly paused entries, including a hybrid whose event half must not be subscribed. Healthy cron, event, and hybrid entries still register. A repeated start or stop/start must not duplicate listeners. Do not clear debounce history merely to implement this change; preserve existing stop/start debounce semantics.

`CronScheduler.add()` must continue throwing scheduling failures to creation/resume callers. Do not silently pause a brand-new failed creation and return tool success.

The same startup error boundary naturally covers a restored workflow state whose timer resolver throws; preserve all existing workflow eligibility checks. Do not add workflow validation or migration rules to this PR.

### 4. Inspection and recovery behavior

Append `pause.reason`, when present, to `LoopList` output and to the `/loop` inspection detail. Retain current pause-kind output. The reason must be inspectable in headless mode and survive session/file restoration. No dedicated recovery event or new tool is required.

A quarantined entry counts toward the existing controller cap, like any other paused controller. The user may delete it with `LoopDelete`, then create a corrected schedule. `/loop` resume retries preflight and leaves it paused if the schedule remains unavailable. A later cron-parser upgrade must not automatically resume it. Explicit resume is required, and the original lifetime/fire cap still applies.

Existing expired entries follow current recovery expiry rules before scheduler startup. Do not retain expired ordinary controllers just to quarantine them. Memory-scoped quarantine disappears with its memory scope, as expected.

### Rejected alternatives

- Tool-only try/catch is insufficient. It leaves old snapshots broken and persists known-bad input before rollback.
- Preflight-only validation is insufficient. Historical snapshots and later registration failures still need handling.
- Catching the entire startup and returning is insufficient. It still prevents healthy controllers from restoring and hides the failed entry.
- Silently dropping the bad entry destroys the user's prompt and evidence. Pause it instead.
- A new quarantine status/schema adds migration work without adding behavior that paused entries plus a reason cannot express.
- A global snapshot rollback can erase healthy concurrent/shared-store changes. Clean up by the failed controller's ID only.
- Extending cron semantics here creates unnecessary dependence on A06. A03 must handle either resolver success or resolver failure safely.

## Risks and review decisions

| Review question or risk | Recommended resolution |
| --- | --- |
| Will preflight duplicate expensive cron resolution? | Yes, creation preflight and timer registration may each resolve once. Keep the existing bounded resolver and no cache in A03. Measure the targeted test time; A06 can improve calendar search without weakening preflight. |
| Does "invalid" mean impossible or just beyond today's resolver horizon? | Use `Schedule unavailable` and preserve the underlying error. Do not label every resolution failure mathematically impossible. |
| Could a catch hide disk corruption or programming errors? | Wrap only next-fire resolution in the dedicated internal error type. Catch only that type during startup. Let store/persistence failures fail visibly. |
| Should quarantine delete entries to avoid the cap? | No. Retain paused entries and explain that users may delete them. Preserve the cap as it is. |
| Should resuming retry forever? | No. One explicit resume attempt runs preflight once; failure retains paused state. No background retry or auto-resume. |
| Can rollback guarantee durable cleanup under arbitrary I/O failure? | No. Attempt both cleanups, report residual controller ID and errors, and rely on startup quarantine for persisted bad schedules. Do not promise atomicity across session-log and file-mirror failures. |
| Does preflight fix crash boundaries across shared-store writers? | Only known schedule failures before mutation. Registration rollback is ID-local and synchronous within one runtime; shared-store ownership and power-loss behavior are not solved here. |
| Will repeated start reset hybrid debounce? | Do not change `lastFireTime` clearing policy. Test duplicate-listener prevention and existing debounce behavior separately. |
| Is manual recovery safe after a parser upgrade? | Require explicit resume, keep existing expiry/cap restrictions, and retain original schedule text. No silent schedule rewriting. |

No external API decision, dependency installation, or missing evidence blocks implementation. A storage write failure is an operational boundary that tests must expose, not a design blocker requiring this PR to repair all persistence semantics.

## Definition of done

- [ ] Impossible cron and unschedulable hybrid creation fail before allocating an ID or persisting a snapshot. Tests compare full before/after snapshots and persistence calls.
- [ ] Late registration failures remove the new entry and its partial registrations, preserve healthy entries, and report any cleanup failure without false success.
- [ ] A legacy poisoned snapshot loads; only the bad controller becomes paused with a retained, bounded reason. Healthy cron/event/hybrid controllers restore and a healthy emitted event produces actual fire evidence.
- [ ] The pause survives both session snapshot and file-store round trips. A second reload does not retry or rewrite an already paused entry.
- [ ] Manual resume of an unavailable schedule leaves its saved paused record unchanged and gives a visible error; a valid explicit resume still works.
- [ ] `LoopList` and command inspection show the recovery reason and the README explains deletion/correction/resume behavior.
- [ ] Healthy schedules beyond the controller lifetime use existing expiry handling rather than quarantine; limits, defaults, dynamic semantics, and skip rules remain covered.
- [ ] Dedicated `loop-creation-recovery.test.ts` regressions pass with no skipped required cases. Red-before/green-after evidence includes the actual store and event-fire assertions.
- [ ] The exact A03 `Known audit gap` test is converted to positive expectations. Unrelated audit coverage and the slash-command positive regression are retained.
- [ ] `npm run typecheck`, the full `npm test`, and `git diff --check` pass on the final implementation commit. Record commands and outcomes, including any known unrelated characterizations still present.
- [ ] Documentation is updated without rewriting historical evidence. Any live smoke check records the disposable procedure, capped result, and cleanup, or the PR states that live verification was not run.
- [ ] The reviewed diff contains no unrelated production, package, tool-schema, cron-dialect, worker, or monitor changes.
- [ ] A scoped implementation commit and PR include the source reasoning, test evidence, recovery behavior, persistence/cancellation boundaries, and dependency/merge-order notes. Resolve review feedback and rerun affected checks after rebases.

These checks establish the specified creation and recovery behavior. They do not prove absence of every possible regression, failure mode, or crash boundary.
