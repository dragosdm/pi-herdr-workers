# A01: Do not mistake monitor shell startup for command execution

## Status and goal

Specification only. This document does not implement the fix.

A successful new-monitor result must mean that Herdr accepted one submission of the requested command after the target pane was observed at its shell. A foreground startup helper is not evidence of that submission. If readiness cannot be established within a bounded wait, retain the pane handle and report that the command was not submitted.

An existing busy monitor must still be attachable without interrupting or restarting it. Attachment is an observation, not proof that its foreground process is the requested command.

The impact is a missing server, build or other requested command with a success response. Follow-up work may proceed under a false assumption. Blind retries can also duplicate work if a command was actually submitted but its acknowledgement was lost.

A01 has a direct deterministic cause. Do not generalize this confidence to A04. The worker-readiness audit measured missing accepted readiness on fresh launches; it did not capture the exact interprocess timing that would prove its suspected startup race. A04 is outside this change.

## Scope and compatibility

Fix new-monitor startup, explicit retries after a known unsubmitted startup, and the result language needed to distinguish submission from attachment. Include recovery and cancellation tests for these paths.

Preserve:

- Public tool names and input schemas: `MonitorCreate { command, description? }`, `MonitorList {}`, `MonitorStop { monitorId }`.
- `commandKey()` hashing of cwd, NUL and trimmed command; existing `mon:<key> ` labels and command quoting.
- The case-sensitive `Monitor` tab name, current workspace selection, down-split/no-focus behavior and reuse of an available unlabeled root.
- The current limit of 25 tracked running/unknown monitors and monotonic IDs. Do not silently change the cap's semantics or redesign accounting.
- Same command and cwd reuse the same eligible pane. A later explicit create may rerun a previously submitted command once that pane is idle. This is not cross-call exactly-once execution.
- Existing busy labeled panes can be attached without `pane run`, `ctrl+c`, rename or close. Existing foreign busy roots must not receive command input.
- Restore never starts a command. Dispose never kills a pane. New sessions do not inherit another session's handles.
- The status union `running | idle | stopped | error | unknown`. Status remains observational rather than an exit-code or process-identity guarantee.

Non-goals: fixing tail parsing, changing shell integration or the Herdr CLI, tracking command PIDs/exit codes, supporting more shells, preventing daemonization, cross-process launch locking, changing monitor tab case matching, replacing Pi's durability model, and any loop or worker fix in A02–A11.

## Recommended design

### 1. Separate pane reuse, launch evidence and this call's outcome

Add an optional persisted field to `HerdrMonitor`:

```ts
launchState?: "pending" | "submitted" | "uncertain";
```

- `pending`: this manager has claimed the pane for this monitor but has not attempted `pane run`. A readiness timeout, pre-submission cancellation or failed probe does not clear it.
- `submitted`: `pane run` returned a successful acknowledgement for the last submission. It does not establish that the command is still running or succeeded.
- `uncertain`: submission may have happened, or the process ended before its acknowledgement was recorded. Never report this state as confirmed submission.
- Missing field: legacy or adopted handle with no submission evidence. Preserve existing observational attachment/explicit idle-reuse behavior, but never invent submission history.

Keep `reused` about finding an existing command-labeled pane. Do not use it as the action taken by this call.

Change the internal `create()` return type to `Promise<HerdrMonitor & { createAction: "submitted" | "attached" }>`. Return a shallow result object with `createAction`; do not put that transient field in `byId` or snapshots. Existing field access stays compatible. There are no external RPC/schema changes.

Keep `herdr-monitors.snapshot.v1` and its envelope. The new field is additive and optional. `restore()` must accept old snapshots, preserve valid launch states, normalize an unrecognized launch state to `uncertain`, and still reset process status to `unknown`. Do not infer submission from a legacy `running` status. No disk rewrite or background migration is needed. The next normal snapshot carries the field.

### 2. Know whether the pane is newly claimed

Have `ensureMonitorTab()` also return `created: boolean` internally.

- If it created a tab, claim its returned root pane and wait for readiness there. Do not split just because this fresh root is running a startup helper.
- In an existing tab, attach/reuse a matching command label as today.
- With no match, an existing single unlabeled root may be claimed only after the current positive shell check. Busy or unclassified existing roots are not available; split instead. A failed CLI request is an error, not permission to claim that root.
- A split pane or newly claimed root gets `launchState: "pending"`, `status: "unknown"` and a saved handle before readiness waiting or command submission.
- Persist the handle as soon as its pane ID is known, before the rename, so cancellation or a rename failure can name the retained pane. A failed rename leaves an inspectable unknown/error handle and no command submission. On retry, a pane whose expected label is absent is not silently claimed from that stale handle.

All pane acquisition remains in `serialize()`. Calls that fail must release the queue. Treat `pending` as authoritative even if a subsequent explicit create finds its now-labeled pane and sets `reused: true`. That call must wait for readiness, not attach to its startup helper.

### 3. Use bounded, abortable readiness observations

Factor foreground inspection into an internal discriminated result: `ready`, `busy`, or `unknown`. Keep CLI execution/JSON failures separate from a valid but incomplete process observation.

A `ready` observation requires:

1. A positive safe integer `shell_pid`.
2. A nonempty `foreground_processes` array.
3. Every entry has a positive safe integer PID equal to `shell_pid`, and its name is one of the existing exact names `bash`, `zsh`, `fish`, `sh`.

A valid nonempty list containing another foreground PID or a non-shell name is `busy`. Missing fields, an empty list or malformed PID/name entries are `unknown`. Do not classify absence as readiness. Do not expand the shell allowlist in this PR.

For `pending` monitors, both `busy` and `unknown` mean wait and observe again:

- Set a monotonic deadline of 5,000 ms when readiness waiting starts. Time spent acquiring a pane is outside this readiness budget and remains bounded by existing CLI timeouts.
- Probe immediately; after an unsuccessful observation, wait at most 100 ms before the next probe, capped by the remaining deadline.
- Every probe uses the smaller of 15,000 ms and the remaining readiness budget as its CLI timeout. A deadline signal must also cover the in-flight probe. Extend the internal command helper with an optional timeout override while retaining its existing default for other calls.
- Use an abortable timer, not a shell `sleep`, busy-spin or an unbounded retry. Clear timer/listener resources on every completion path. Allow deterministic clock/wait injection through optional internal manager dependencies for tests; preserve `new HerdrMonitorManager(exec)`.
- At or after the deadline, do not submit even if a delayed probe returns `ready`.
- A CLI nonzero exit, killed request or malformed JSON fails immediately with its cause. A valid `unknown` observation may recover on a later probe within the deadline.
- Combine caller cancellation and manager lifetime cancellation for the whole operation, including queue entry, observations, timer waits and the final pre-run check.

When a ready observation is obtained, validate the command label with `ownsPane()` before submitting. For a pending launch, this check shares the remaining readiness budget and deadline signal; check the deadline again immediately before submission. Ownership failure sends no command or signal and produces an actionable error. No amount of process inspection creates a transaction with terminal input; document that another actor can change the pane after inspection. Do not claim this eliminates that external race.

For a non-pending, already-labeled pane, retain current behavior: a valid busy observation produces `createAction: "attached"` without command input; a ready shell can receive a new explicit submission; unknown process information produces an error. No readiness wait should interrupt an existing monitor.

### 4. Submit once and record uncertainty honestly

Immediately before calling `pane run`, persist `launchState: "uncertain"`. This closes the specific crash window where a surviving snapshot would incorrectly say no submission was attempted. Check cancellation before crossing this boundary. If that persistence throws, do not invoke `pane run`.

Invoke `pane run` at most once per `create()` invocation, with the existing `cd -- <quoted cwd> && <command>` construction. Do not retry command submission on timeout or error.

- Successful acknowledgement: set `launchState: "submitted"`, `status: "running"`, update `startedAt`, persist and return `createAction: "submitted"`.
- Failed, aborted or ambiguous submission: retain `uncertain`, set status `unknown`, persist when the manager is still live, and fail with a message identifying the pane and saying submission may have happened and inspection is required before retry. If failure-report persistence also throws, preserve the launch uncertainty in memory and include both causes without masking the inspection warning.
- Readiness timeout: retain `pending`, status `unknown`, and fail with `Monitor #<id> command not submitted: shell readiness timed out after 5000 ms; inspect pane <paneId> before retrying.` No success tone, `started`, or `attached` result is allowed.
- Other failures before submission: retain `pending` if applicable and identify that the command was not submitted. If acquisition succeeded, include the retained pane ID. If acquisition itself was ambiguous and returned no ID, do not invent a recoverable handle or close a guessed pane.

A later explicit create on an uncertain/legacy handle remains an explicit user-authorized retry or attachment under the existing contract. It is not retried automatically by restoration or within the failed call. If busy, its result says only that it attached to an observed foreground process and did not submit a command. If ready, it may submit once. Documentation must warn callers to inspect after an uncertain error before issuing that explicit retry. Adding a separate force/reconcile tool is out of scope.

The append-before-launch rule follows existing session storage guarantees. It does not prove power-loss durability, and an old snapshot or an untracked pane can lack the launch evidence. Old binaries also ignore the new field. Do not advertise safe automatic downgrade/replay of pending launches.

### 5. Keep list, stop and tool results consistent

`refresh()` must not turn a `pending` monitor into `running` merely because a startup helper is busy. After a successful ownership check, leave its monitor status `unknown` until a command is submitted, even if a shell is now ready. `MonitorList` should show the launch state, for example `command not submitted`, in that row. It may still attempt the existing tail read; A02 owns tail reliability.

`stop()` must return false for `pending` monitors and send no `ctrl+c` to startup helpers. Preserve its current ownership and foreground checks for other monitors. No automatic pane cleanup is part of startup failure handling.

`MonitorCreate.execute()` must render the transient action, not derive it from `reused`:

- `submitted`: `Monitor #<id> command submitted (new pane)` or `(reused existing pane)`. Explain that the pane remains open. Do not claim command completion or application readiness.
- `attached`: `Monitor #<id> attached to existing busy pane; no command submitted`. Include that foreground identity is observational, especially for legacy/uncertain handles.
- Error: preserve error tone and `isError` behavior from `textResult`; replace the misleading generic `Monitor was not created` summary with `Monitor command not submitted or submission uncertain`. The detailed message distinguishes the two and names any retained pane. `loop/tools/tool-result.ts:34`, `textResult()`, throws for error tone, so the thrown message itself must carry this information; do not rely on error details being returned. Update the widget before that throw on the failure path as well as on success.

Concurrent list calls must not overwrite launch evidence or cause a pending startup to look successful. Cancellation while queued or waiting must produce zero later command submissions. Dispose cancels outstanding readiness work, suppresses later `onChange` calls and leaves all panes intact.

## Alternatives rejected

- Always attach when busy. This is the faulty behavior.
- Always run in a newly created pane. It can type into a startup helper or another foreground program.
- Sleep once for a fixed duration, then run. Elapsed time is not positive shell readiness.
- Retry `pane run` after a timeout. It can duplicate a command that was already submitted.
- Only keep a local `newPane` flag. A failed startup followed by retry or reload would lose the distinction and incorrectly attach again.
- Add PID tracking, shell sentinels or a new lifecycle protocol. Those might support stronger guarantees but are not necessary for this bounded fix and would change command semantics.

## Risks and review decisions

| Question or risk | Recommended resolution |
| --- | --- |
| Is five seconds enough for all shell configurations? | Use a bounded five-second readiness budget for this fix. A slower startup produces an honest error and retained pending handle; the caller can inspect and explicitly retry. Do not add a public tuning parameter without measured need. |
| Does a shell foreground observation prove application readiness? | No. Report command submitted only after CLI acknowledgement. Do not promise application startup, exit status or foreground command identity. |
| Can shell initialization be busy inside the shell itself? | Yes. Retain the existing process-info readiness contract and document that it is not a shell prompt handshake. Validate the supported Herdr/shell combination live; a future integration protocol would be a separate change. |
| Why persist more than a local new-pane flag? | Pending state prevents repeat false attachments across readiness errors and reload. Uncertain-before-run prevents a surviving snapshot from asserting no attempt after an interrupted launch. |
| Can the new field guarantee recovery after abrupt power loss? | No. Keep Pi's existing storage/durability caveat and no-automatic-replay behavior. Do not claim exactly-once external effects. |
| Can unrelated foreground processes be interrupted on retry? | Create never sends signals. Pending stop is rejected. Existing non-pending stop retains its current ownership/process guard; stronger PID attribution is outside A01. |
| Does global serialization delay other monitor operations? | Yes, by the bounded readiness wait plus bounded CLI calls. Keep serialization to prevent duplicate acquisition in one manager. Test failure releases the queue; do not replace it with an unreviewed locking scheme. |
| Is changing success text breaking? | Tool schemas remain unchanged. Correct misleading text and document it; test structured tone and action. Do not retain a false `started` claim for wording compatibility. |
| Are new library dependencies needed? | No. Use Node timing/abort facilities already available under the supported runtime. |

No specification blocker was found. Live verification requires authorization for a disposable workspace and an installed Herdr CLI; lack of that environment is a verification blocker to record, not permission to claim live success.
